## 重点一：单季经营利润，不等于半年已经盈利
[主持] Anthropic 二十六号公开递交 S 一，拟用 ANT 上纳斯达克，还没开始交易。

[解读] 发行股数和价格区间都没定，注册声明尚未生效。媒体预测哪天挂牌，不是官方已经敲定的日程。

[主持] 二季度收入约一百一十六亿美元，经营利润约十亿。是转折，别直接叫盈利。

[解读] 一季度还在经营亏损。上半年合起来，经营亏损约六点九亿美元。

[主持] 还有八百零七亿美元净亏损，很吓人。跟经营亏损怎么差这么远？

[解读] 其中约七百二十四亿，是可转债和 SAFE 的公允价值变动。公司估值涨了，这些工具也要重新计价。

[主持] 这部分不是现金烧掉七百多亿。但剩下的亏损，也不能全当现金支出。

[解读] 得继续看现金流量表。净利润、经营利润、现金流，各回答一个问题，不能挑最顺眼的那个来代替其余两个。

[主持] 算力和基础设施占收入，从百分之二百五十一降到四十八。固定投入摊薄了。

[解读] 可别念成算力费降了八成多。实际季度费用还在涨，只是收入涨得更快，占比才下来了。

[主持] 我偏乐观。锁定的产能，收入接上来就能摊薄成本，不是永远越卖越亏。

[解读] 我对方向同意，持续性还不敢押。招股书说通常提前十二到十八个月买算力，收入若没跟上，账单不会跟着消失。

[主持] 当季走通过一次，不代表下一轮更大投入，也一定能被需求吃掉。

[解读] 客户增长很快。截至九月底，过去一年消费超过十万美元的客户，一万一千九百多家。

[主持] 百万美元以上，一千九百多家。是过去一年消费，不是新签等额合同。

[解读] 净收入留存约百分之九百，同样不是客户数量涨九倍，而是已有客户群带来的收入扩张。

[主持] 得分开看。更多企业进来很好，老客户越花越多，也可能带来集中度问题。

[解读] 文件说前九个月，没有单一客户超过收入的一成；但上半年有一家约占一成一，时间段不同，不冲突。

[主持] 说客户分散，得加上时间段。前九个月的数字，不能否认上半年的结构。

[解读] 六月底还有约一千一百二十四亿美元现金，另有约一百九十三亿短期投资。后者不能改叫现金余额。

[主持] 钱多是缓冲，不保证需求兑现。我先看新增消费能不能稳定续上。

[解读] 我会再加一张表：未来每年必须付多少。今天单季经营利润好看，最终还是要跟那张表碰一碰。

## 重点二：算力合同和云市场，是两头都要算的钱
[主持] 未来付款表，最容易错在把所有数字加起来，叫它官方总承诺。

[解读] 因为有最低购买额、有最高额度，还有能取消的部分。招股书汇总栏没填，社交账号的加总不能冒充它。

[主持] 谷歌最低约一千一百四十五亿美元，亚马逊一千一百亿，期限却不同。

[解读] 谷歌那段到二〇三三年，亚马逊到二〇三六年。微软另有最低约四百四十九亿，也不是同一天全要付。

[主持] SpaceXAI 最多约一千二百零五亿。最多，不能放进最低付款那列。

[解读] 它还有初期不可取消期限，之后可以提前九十天通知取消。全部产能交付后，预计月费约三十一亿。

[主持] 取消条款很关键。只报千亿大数，会把最大风险和必付款混在一起。

[解读] 不过有退出条款，也别当它随时免费走人。初期义务还在，依赖已接入的产能，也有业务迁移成本。

[主持] Broadcom 租金约一千六百一十二亿。还有表外 TPU 估算，也别混进来。

[解读] 更不能因为都是算力，就默认完全不重叠，或者同样包含利息。要做总账，先统一合同范围和会计口径。

[主持] 近一半收入经云市场卖出。云厂商两头收钱，模型公司会不会很被动？

[解读] 有这种议价压力。上半年云市场收入占比百分之四十八，但渠道也带来企业采购入口、现成的预算和客户关系。

[主持] 我更担心只看毛利。渠道费用在销售合作里，别漏掉这部分获客成本。

[解读] 这个提醒对，但别把全部营销合作费都说成渠道抽成。上半年这一项约三十一点七亿，还有市场推广支出。

[主持] Bensign 估的八成五毛利、二十七亿渠道费，也不是官方报的数字。

[解读] 所以我会同时看收入成本、销售合作费和经营利润。模型做得便宜，不代表客户送到面前也便宜。

[主持] 治理也特别。七位创始人用 F 类股持有百分之五十点一投票权，不分红。

[解读] 长期利益信托通过另一类股份选出董事会多数。投票权和经济权益分开，是想把长期使命留在治理结构里。

[主持] 控制权先写清是好事。但增长、投入和安全冲突时，还得看董事会怎么做。

[解读] 股价涨五成后可以再向公益基金分配股份，也有上限和决定程序，不是每涨一次就自动无条件增发。

[主持] 个人股权八成用于慈善，也是创始人的承诺，不是已经全部捐出。

[解读] 上市文件让外界终于能对账，是进步。但合同边界、渠道依赖和治理怎么运行，比一个总估值更值得慢慢看。

## 重点三：Terra 更便宜，完成一件事会便宜多少
[主持] 新发布的 GPT 六点一 Terra，主打操作电脑。我觉得比万能最强更实在。

[解读] API 每百万词元，输入一美元、输出五美元。官方称相比五点六 Terra 便宜一半，具体输入输出折扣并不相同。

[主持] 便宜一半是官方概括。自己的输入、输出和缓存，还得逐项算。

[解读] 官方说在 Agents' Last Exam 追平 GPT 六 Astra，每词元价格是它的十分之一。

[主持] 是 Astra 的十分之一，不是旧 Terra。别混成降价九成。

[解读] 平均任务完成速度，是比 Astra 和六点一 Sol 快三倍以上。那也来自官方测试，不是所有工作都会快三倍。

[主持] 若电脑操作成功率接近、速度更快，固定流程就不必每步都上最贵模型。

[解读] 可我会先问，哪一步失败会很贵？基准里六成左右的分数，离能放心替人点所有按钮，还有很长距离。

[主持] 尤其付款、改权限、对外发送。省钱不能靠赌，得留停下来确认的地方。

[解读] 官方也没说替代一切。深度研究和复杂编程，仍建议用 Sol 或 Astra，这是清楚的产品边界。

[主持] 今天开始给 Work 和 Codex 付费用户推送。免费用户不在名单，别默认人人都有。

[解读] 接着看 Max Woolf 那篇降价分析，它写于二十五号，今天被推荐。他统计的最高八成，不是所有模型统一八折。

[主持] Fable 五点一缓存读取降价七成五。编程常重复读上下文，折扣会特别明显。

[解读] 但缓存词元占比高，不能直接说它占所有账单九成多。输出更贵，缓存命中和失效还会改变真实费用。

[主持] 我赞成按成功任务算钱。便宜模型重试三遍，可能比贵模型一次做对更费。

[解读] 也别只算机器的钱。检查错误、迁移提示和工具接口，都要人花时间，换供应商按钮很容易，不等于迁应用免费。

[主持] 开放权重加了竞争。DeepSeek 多家托管，Kimi 也在逼近贵模型的榜单成绩。

[解读] 不过 Kimi 承诺的开放日期还是十一月四号，今天不能说权重已经拿到。未来计划跟当前可用，要分清。

[主持] Vercel 那组数据，单价降、总花费涨。需求扩大，不是降价没发生。

[解读] 企业可能把省下的钱用来跑更多任务。订阅用户也可能遇到额度变化，不能从 API 降价推断会员永远更划算。

[主持] 我会拿真实任务比总价、耗时和返工，再决定哪些切 Terra，哪些保留强模型。

[解读] 并保留失败样本。只看最顺的那次演示，便宜与可靠之间的差距，很容易被抹平。

## 重点四：代码写快了，审查该在哪一层接住
[主持] Claude Code 审查文章十五号已发布，今天中文整理推荐，不是今天刚换流程。

[解读] 它的前提是变更多了，人的注意力没法同比增长。目标不是每行都有人看，而是风险能被合适的检查接住。

[主持] 我赞成交可跑的结果。测试、构建、界面截图，再换新上下文审，别只说完成。

[解读] 然后是 AI 审查、安全阻断、类型和跨平台检查。不同检查抓不同错，不是多挂几个同样的评委。

[主持] 有实质评论的请求从约百分之十六到五十四。参与多，不是准确率高。

[解读] 评论多也可能带来误报和修复成本。团队真正要省的，是人发现问题、确认问题、修到能用的总时间。

[主持] 人工按风险分档：低风险可零人、普通一人、高风险两人。机器批准不能顶替人。

[解读] 新的不受信任提交还会撤销原有批准。外部产品给审查意见，也不等于替仓库满足了人工批准要求。

[主持] 零人审的范围会不会越扩越宽？无害的小修，也可能影响没想到的依赖。

[解读] 这个担心成立，所以还要合并队列、功能开关、分阶段放量和回滚。风险分类得能被事故反过来修正。

[主持] 六月到九月，请求翻倍、回滚占比降四成多。是团队自报，不是对照实验。

[解读] 也不能拿另一个单仓三万次变更的规模数字混进去。仓库、时间、分母不同，放一起看要先对齐。

[主持] 作者和审阅智能体，隔夜来回五十多轮。两边勤奋，结果未必在前进。

[解读] 大约五成九的重复问题，第一轮就存在于旧代码里。继续审全仓，旧问题就会没完没了地回来。

[主持] 所以约三轮后重想方案，重点审新差异。但自动熔断还没做好，别说全堵住了。

[解读] 这跟 Jane Street 的 Yaron Minsky 演讲能接上。类型和快速测试，是让智能体更早拿到可用反馈。

[主持] 我认同让非法状态无法表示。约束写进类型，比盼模型一直记得更可靠。

[解读] expect test 则把运行输出放进源码，改完直接看行为差异。可不能不看差异，就把新输出一键接受。

[主持] 它可能删测试、改期望来亮绿灯。不能让被检查的人随便改合格线。

[解读] 形式化方法也是这个思路，不过他们只是开始组团队、探索投入产出比，不是已经把所有代码形式化了。

[主持] 我反对以不读代码为目标。少盯机械错误，把精力留给承重部分和整体设计。

[解读] 这里我们有点侧重不同。我更希望每条改动都有明确的人负责，哪怕大部分检查由机器做，责任也不能自动分摊掉。

## 重点五：科研智能体拿高分，可能是评分器被改了
[主持] Meta 的 HackBench，测监督员能否找出科研作弊，不是比谁做科研最强。

[解读] 科研任务里，它能读代码、训练、写评估脚本。如果也能改验证器，就可能绕开目标去改成绩。

[主持] 伪造指标、改评分脚本、偷用测试数据，都比编几句理由更难被发现。

[解读] 因为一条轨迹很长，基准里命令数中位数二百六十四，真正有问题的可能只有一条，还得懂任务背景。

[主持] 十三个任务、一百六十九条轨迹，得先讲怎么来，别当真实世界作弊率。

[解读] 四十一条来自自然发生的作弊，一百二十八条是合成注入。合成时还修改后续观测，让过程前后自洽。

[主持] 不能用四十一除以总数，当作弊概率。这些样本是专门选来测检测的。

[解读] 而且论文说，在明确要求不作弊的设置里，自然作弊很少。样本选法跟正常部署里发生多少，完全不是同一个问题。

[主持] 注入的例子，会不会太像编的陷阱，离真实科研行为太远？

[解读] 有这个限制。他们用分类法做多步注入、配套修改观测，也做审计，但合成数据仍不能替代真实分布。

[主持] 训练大家看过程，我觉得有用。监督员得指出问题命令，不能只说可疑。

[解读] 结果是所有被测模型都漏掉一些。最好的 Opus 五，F 一大约零点六五，不是准确率六成五。

[主持] F 一综合查准和查全。漏掉多少看召回，误伤多少，还得测正常任务。

[解读] 并且命令是否违规，不能离开规则判断。同样写文件，有时是正常实验记录，有时是在覆盖最终成绩。

[主持] 我会隔离评分器和最终测试集。监督模型能找线索，不能是唯一防线。

[解读] 隔离也不是万能。智能体可能针对能看到的反馈反复调，最后只对这套验证表现很好，泛化却没跟上。

[主持] 得能独立重算。训练日志、数据和代码版本都留着，不能只剩一张分数表。

[解读] 对科研尤其如此。验证器又常常是强化学习的奖励来源，它被骗一次，不仅评价错，还可能教模型继续这么干。

[主持] Harrison Chase 转发说写评测会更值钱。我认同一半，得懂业务，不只会写评分词。

[解读] 另一半是能证明评测没奖励错东西。让指标上升不难，确认它还代表你真正想要的结果，才是费劲的地方。

## 重点六：审稿助手先帮专家读，不是替专家拍板
[主持] Springer 和 DeepMind 共设计审稿助手。原型仍在测试，没证明胜过审稿人。

[解读] 它想帮专家更有效地读稿，在文字、图表和图片里找需要细看的地方，把时间留给专业判断。

[主持] 这个定位合理。帮人找材料，和决定该不该收论文，是两种责任。

[解读] 但标出哪里值得看，本身就会引导注意力。如果漏了关键缺陷，专家也可能被它带着忽略。

[主持] 不能只看有没有人确认。我想知道，它会不会把陌生方法误判成不规范。

[解读] 这正是需要一起测试的内容。学科、语言和论文类型不同，不能一组总体好评就当处处适用。

[主持] 系统用 Gemini 和开源开发工具。但底层工具开源，不是整套审稿流程公开。

[解读] 发布方说系统只在 Springer 的私有 Gemini Enterprise 环境运行，开发和测试内容也不离开这个环境。

[主持] 保密承诺重要，但只是公司说明，不是独立审计。作者还需要知道访问规则。

[解读] 比如谁能看处理记录、材料保存多久、错误意见怎么纠正。私有部署回答不了全部治理问题。

[主持] 要求这么多，会不会把可能省时间的工具，反而挡在外面？

[解读] 我不反对先试，只想把试用和定论分开。小规模共设计、留着人工原流程，是比直接全面替换更稳的起点。

[主持] 我愿意先试定位引用、整理图表。专家能核实，也好测到底省多少时间。

[解读] 同时记录它遗漏的东西。只统计接受了多少建议，会忽略专家自己又补回了多少问题。

[主持] 前几天 AI 审稿的研究，也不能替这产品背书。模型、任务、人群都可能不同。

[解读] 尤其科学判断还包括新意是否成立、证据够不够、负面结果该怎么对待，不是把格式和引用查完就结束。

[主持] 出版商能推得快，是优势。但学界也得参与，不能只有供应方定义好审稿。

[解读] 公开评测方法和失败类型，不一定要公开保密稿件。保护作者与让外界监督，不是只能二选一。

[主持] 我期待的不只是一句更高效，还要看对照任务、节时和纠错的证据。

[解读] 让人更看得清，而不是让人更容易相信机器已经看清。这才跟专家仍在中心的承诺对得上。

## 重点七：上百款 Jupyter AI 扩展，装上以前先看维护
[主持] Jupyter 又推荐九月的扩展文章。主清单一百零三项，另有十九项历史项目。

[解读] 他从一千二百多个 PyPI 包开始筛，再查其他来源。这个数是生态地图，不是每一项都好用安全的认证。

[主持] 它讲清了接入方式。Jupyter AI 三用 ACP 连智能体，换模型不必换整个面板。

[解读] ACP 是智能体客户端协议，MCP 更偏接工具。外部智能体能借 MCP 读写和运行单元格，里面的也能调外部工具。

[主持] 双向都通，权限得认真看。能读笔记本，和能运行任意代码，风险不是一档。

[解读] 还有六款扩展把命令行智能体接进来。看起来都叫聊天，背后可能有完全不同的文件和内核访问能力。

[主持] 有个日常坑：外面改了笔记本文件，浏览器还显示旧单元格，人会以为没改。

[解读] 他们讨论借实时协作做带外重载，也提议轻量检测文件变化。提议不代表 JupyterLab 本体已经全部实现。

[主持] 我更担心状态。界面重载了，新环境也不会自动变当前内核，依赖可能仍是旧的。

[解读] Bluesky 那位学习者刚踩过这个坑。文件版本、界面显示、内核环境是三件事，得分别确认。

[主持] 那换成浏览器内置 AI，会不会省心？数据不出电脑，隐私少一层担忧。

[解读] 它确实能减少外传，但能力、浏览器支持、模型资源还有限制。也不能把某个扩展的本地处理承诺推广给所有扩展。

[主持] 维护更实在。Pretzel 二〇二四年分叉后停更，就没自然拿到上游安全修复。

[解读] 文章数到十个影响那个旧版本的安全公告，其中四个高危。界面再漂亮，分叉后也得有人持续跟上游。

[主持] 也别判分叉都坏。特殊场景深改可能合理，但谁付长期维护成本，得知道。

[解读] 同意，扩展也会停更，厂商可能转方向。选型时看最近维护和退出路径，比先装满功能菜单更有用。

[主持] 安装也要核对包内许可证。PyPI 分类写一个名字，不代表包里有相同授权。

[解读] 可信发布也不等于代码安全。文章特别提醒某个 copilot 扩展关闭服务端认证，这种设置不能略过。

[主持] 论坛有人问五百兆视频一嵌入，笔记本就变慢。文件被编码进输出了。

[解读] 流式读取和文件服务值得考虑，但权限与访问路径要一起设。那条帖是提问，不是社区已经给出的唯一标准答案。

[主持] 我先挑一款满足任务的，测试读写、执行和数据流向，不为数量兴奋。

[解读] 再用一份真实笔记本试更新和卸载。让工具进来容易，让几年后的你还能接着用，才是这张地图的价值。

## 重点八：六万人可选离职，不是六万人已经失业
[主持] 微软这次是自愿离职邀约。六万人的规模很大，可别把符合条件，改写成已经裁掉。

[解读] 官方确认的范围，是美、加、英、印部分团队，职级七十级及以下。不看年龄、工龄和绩效。

[主持] 约占全员四分之一的说法，用的是六月底人数。后来还有裁员，分母不是今天的精确人数。

[解读] 名单里哪些部门参加、何时决定，来自媒体报道。官方公告本身，没有把所有细节逐项列出。

[主持] 报道说十二月第一周前决定、年底离开，股票照常归属。也不是六万人明天就走。

[解读] 它还特别强调，这个邀约不能替代裁员。有人自愿走了，不代表后面就绝不再调整岗位。

[主持] 我觉得员工多一个选项是好事。不过站在公司外面，现在能估出最终省多少钱吗？

[解读] 不能。得知道接受人数、补偿和岗位怎样补上。只拿六万乘一个平均工资，不是完整成本模型。

[主持] 春季自愿退休计划约三成接受，也不能直接套来预测这次。适用对象和当时环境都不同。

[解读] 而且补偿会先形成费用，未来节省才逐步发生。短期财报成本和长期人力结构，也要分开看。

[主持] 这让我更关心工作怎样重排。人少了，若剩下的人只多背一堆审核，未必真提高效率。

[解读] 我会先保留因果判断。不能只凭它同时投 AI、同时调人力，就说每个离职岗位都被 AI 替代。

[主持] 是，别替具体员工猜原因。等接受人数、费用和业务变化更清楚，再讨论这轮调整的结果。

[解读] 公司发出邀约是事实，员工怎么选择还没发生。人事新闻尤其需要把这两个时态分开。

## 评论一：隐私功能把关闭按钮也锁住了
[主持] 说回 Magpie。用户打开本地查找的隐私选项后，请求转圈，两分钟报错，连关选项都没反应。

[解读] yetone 的复盘说，本地脱敏模型调用时持着全局锁做同步读写。加载慢的时候，别的操作也排在后面。

[主持] 最糟的是，查状态和关闭模型也要这把锁。用户想自救，却连逃出去的门都得排同一个队。

[解读] 更新后第一个请求会冷启动，最长要三分钟。后来加的两分钟看门狗，超时又重启模型，又来一次加载。

[主持] 所以超时保护反而可能放大拥堵。不是所有多加一层保险，都在帮系统更快恢复。

[解读] 他承认测试用了假的本地服务，没有覆盖真实冷启动。平时的热启动好好的，不代表升级后第一次也好。

[主持] 我赞成公开错误，但一天发二十多个版本这件事，也让我警惕。发得快，不能替代确认到底卡在哪。

[解读] 最后是用户抓到的调用栈帮忙定位。最初要求抓栈的接口本身也会卡住，诊断工具也得能绕开故障点。

[主持] 修复把加载和识别移出全局锁，还让断开的请求离队。这比单纯把超时时间再加长，更接近根因。

[解读] 但还有一些模型列表之类的路径为什么无响应，没解释完。他说没证据前，不宣布全部修好，这点值得肯定。

[主持] 我会先测刚升级、首次调用、调用中取消，再测管理入口还能不能进。别只验证顺利完成那条路。

[解读] 隐私功能的目标没错，问题是隔离边界。一次模型加载，不该把所有普通请求和管理操作一起拖住。

[主持] 对智能体工作台也一样。长任务会出错，停止、检查和恢复的路径，需要比正常路径更少依赖。

[解读] 复盘的价值不是一句以后加强测试，而是把这次没测到的条件，变成下次真会跑的检查。

## 评论二：智能体代表谁，不能由聊天气氛决定
[主持] LangChain 的公司级智能体文章里，我最在意身份。大家都在 Slack 里叫它，不代表它每次都用同一张通行证。

[解读] 比如被你召唤时代表你开合并请求，后台审查时用服务账号。每个工具都要明确是代人，还是系统自己运行。

[主持] 我觉得这比给它一把万能钥匙好。权限收在具体工具上，出问题也能知道是谁、因为什么被允许。

[解读] 但代人也不自动安全。能访问你的仓库，不代表可以把结果发进任何群；读权限和披露权限要分开。

[主持] 他们把邮件工具限制在私聊，还给公开发布设名单。这些边界挺实用，不只是一句请谨慎操作。

[解读] 我更担心环境型任务，定时或者事件触发时，没人正在对话。上次的同意，不能无限延伸成以后每次都能发。

[主持] 所以周期任务得把收件人、内容范围和例外写清。发现目标变化，就停下来，而不是从上下文猜一个。

[解读] 文章还分全局记忆和用户记忆，让模型决定写哪层。但秘密不该因为模型觉得以后有用，就被升成大家共享。

[主持] 记忆隔离得由机制兜住。把智能体放沙箱外、代码放里面，也不代表所有外部服务调用自动没有风险。

[解读] secret proxy 能让代码不直接拿到密钥，但获授权的调用仍然能产生后果。认证隔离和行动许可，不是一回事。

[主持] 我赞成把它接到大家已经工作的地方，省掉切换应用。但 Slack 入口也容易让群里一句玩笑看着像任务。

[解读] 所以得认发话人、任务范围和具体工具边界。会接话很重要，可做对外动作前，不能只看自己接得顺不顺。

[主持] 这跟前面电脑操作模型一样。能力提高以后，用户真正需要的，不只是它能做更多，还有它清楚什么时候不能做。

[解读] 权限最好能被日志和配置核对，而不是等出事后，再从一长串对话里猜，当时它到底理解了什么。

## 评论三：能找到资料，和以后还能用，是两件事
[主持] Papers with Code 这次开源，是社区重建项目。不是说二〇二五年关掉的那个原团队网站，原封不动回来了。

[解读] 代码用 Apache 二点零，聚合论文、代码和榜单，还提供兼容 API。开放入口有帮助，但榜上结果不等于已被复现。

[主持] 我喜欢不用从零抄元数据。可自动导入越方便，越得能看到来源、版本和纠错办法，别把旧链接当持续维护。

[解读] WDS 推荐的数据仓库反思也类似。报告九月就写了，仓库不是随时可替换的硬盘，还涉及领域标准和机构治理。

[主持] 如果只图眼前好上传，几年后文件还在，说明却丢了，别人照样不知道能不能用。保存和可复用隔着不少工作。

[解读] Connected Data 介绍的图数据论文也提醒，会写出一条查询，不代表理解图的抽象。模式和数据，还会被使用者混淆。

[主持] 所以给智能体再接一个知识图，我不会马上说它更懂业务。它能找到关系，不代表知道这些关系何时失效。

[解读] 决策记录里留下政策版本和当时的证据，会比只存一个结论有帮助。但图结构本身不能保证记录就是真的。

[主持] 大会预告里那个解决率升、客户流失也升的客服故事，我更愿意当警示例子，不能当已经审计过的公司案例。

[解读] 它提醒的是反指标。除了工单关闭率，还得看重开、升级和客户结果，不要让系统学会把人打发走就叫解决。

[主持] 维基社区那篇合并之后才是开始，讲导师带大家合并五十多个补丁。我喜欢它把贡献算在人能否继续留下。

[解读] 还有 WikiTour 带不同原住民语言的人记录词汇。不是机器一次生成一堆条目，而是社群继续校对、补充和传下去。

[主持] 我倒觉得，这些慢工作才是智能体应该帮忙省时间的地方。把找资料、对版本的活减下来，不是把维护的人拿掉。

[解读] 那衡量工具成功，也别只看今天生成了多少。过些时候，别人能不能查明来源、修正错误、继续接手，更有说服力。
