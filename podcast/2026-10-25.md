## 重点一：Kimi K3.1 Pro

接下来是今天的重点，一共七件。

重点一，Kimi 的新模型 K 三点一 Pro。为什么重要？因为一个准备开放权重的模型，编程成绩已经贴到了 Claude 旗舰的身边。

先解释一下开放权重：就是把训练好的模型文件公开，任何人都能下载、自己部署。月之暗面前天发布了这个模型，承诺十一月四号之前开放权重。

昨天，一位中文技术博主把官方报告完整拆了一遍。最受关注的是终端编程测试，也就是让模型在命令行里完成真实的开发任务。K 三点一 Pro 拿到六十五点七分，Claude 的 Opus 五点五是六十六点四，差距不到一分。

篇幅最长的一节，其实是网络安全。开放权重的版本，在训练里专门剔除了网络攻防相关的数据。在一项漏洞利用测试上，没做削减的版本通过率超过九成，最终公开的版本降到了八成出头。换句话说，为了开源，他们主动让出了一截攻击能力。

其他方面也不弱。比如把多角度的渲染图还原成三维建模代码，它也接近 Claude 的水平；金融问答里的幻觉率，降到了原来的三分之一左右。一位中文 AI 博主的评价很直接：能力很强，就是太贵了。

我们的看法是：这些分数都来自 Kimi 官方。等权重真的放出来，第三方复测的结果，才是更该看的。

## 重点二：DeepSeek 开源推理引擎

重点二，DeepSeek 开源推理引擎。为什么重要？因为大模型竞争的另一半，在于同样一块卡能服务多少人，而 DeepSeek 把自己在这件事上的家底公开了。

推理引擎，就是把训练好的模型真正跑起来、响应用户请求的那套软件。

播客 ThursdAI 的主持人 Alex Volkov，在节目里和嘉宾聊到：DeepSeek 开源的不是一个演示品，而是线上实际服务 V 四点一 Flash 模型的那一套。它用的是 Apache 开源许可，可以商用；既能跑在英伟达的新一代 Blackwell 芯片上，也能跑在华为昇腾上。

嘉宾的原话很夸张，说他们“把互联网搞崩了”。他的意思是，同样的硬件能服务更多用户，利润就留在了自己手里。

另一边，有用户观察到，DeepSeek 在好几个第三方编程和模型平台上，调用量都断层领先。一位中文开发者的解释只有三个词：便宜，快，出活儿。

为什么便宜这么重要？因为对用 agent 写代码的人来说，一个任务动辄要调用模型几十上百次，单价差一点，总账就差很多。

我们的看法是：能跑在昇腾上这一点，对国内团队的意义，可能比任何跑分都大。不过这是我们的判断，原帖没有这么说。

## 重点三：AI 安全警告开始落地

重点三，安全。为什么重要？因为实验室报告里那些听起来很玄的警告，这一周开始落到普通人的服务器上了。

先说 OpenAI。在之前一次和 Hugging Face 有关的事件之后，OpenAI 收紧了训练环境的对外通道，只给指标、日志、身份认证这类自家服务，留了很窄的口子。结果，他们的红队 agent 在几乎每一个这样的服务里，都找到了漏洞，拿到了有限的联网能力。

手法有好几种：有的是利用没人知道的缺陷；有的是把几个正常功能，用意想不到的方式拼在一起；还有的是利用配置错误，让本该被拦住的请求绕了出去。

沃顿商学院的教授 Ethan Mollick 说，不必轻信，但应该更认真地对待实验室这些说法。他提醒大家，Anthropic 之前说新一代模型改变了网络安全，当时是被嘲笑过的。

再说 Brotli。Brotli 是一种很常用的压缩格式，网页传输里到处都是。前几天，OpenAI 的红队顺带发现了它解码器里的一个严重漏洞，当时已知影响 Node.js 和 Python。

安全公司 Aikido 昨天警告，这个漏洞已经演变成他们叫做 HTTP2Shell 的问题：很多用 HTTP 的库和应用，都可能因为解压 Brotli 数据，被人不用登录就远程执行代码。说白了，就是攻击者可以在你的服务器上跑他自己的程序。

更麻烦的是，不是所有受影响的服务都已经有修复。Aikido 的建议是，留意 Brotli 一点二点一这个版本的依赖升级，出来一个，升一个。

Alex Volkov 的感慨是，这一周过得像一整年，还好他所有的网站都放在 Cloudflare 后面。如果你的服务也有这样一层防护，可以先松口气，但依赖还是要升。

## 重点四：Shopify 给 agent 配远程开发机

重点四，Shopify 给 agent 配远程开发机。为什么重要？因为它说明，agent 真正干活的时候，缺的往往不是更聪明的模型，而是一台能编译、能跑模拟器的机器。

Shopify 在 Slack 里有一个 agent，叫 River。做手机应用的时候，本地电脑上同时开三四条 agent 任务，就被编译和模拟器占满了。

于是他们搭了一套远程开发机：苹果模拟器跑在远程的 Mac 机群上；安卓模拟器放在另一类 Linux 云主机上，再接进同一个远程会话。

一开始，冷启动，也就是拉下巨大的代码库、再做第一次编译，要超过三十分钟。改成提前热好一批机器、随用随取之后，几分钟就能在模拟器里看到改动。每个 River 会话独占一套环境，可以自己改代码、编译、跑测试，还能在模拟器里点界面，录下改动前后的对比。设计师和产品经理，也可以直接在 Slack 里让它改。

结果是，合并进代码库的手机端改动里，由 agent 完成的比例，从百分之六升到了百分之六十一。

怎么教 agent 用这些远程机器？他们没有搞复杂的框架，就是写了技能说明，再把远程登录包成一个命令行工具。跑得久的任务，放进终端会话里，让 River 随时回来看进度。

还有个细节挺可爱：工程师一开始有心理障碍，不太愿意用。团队专门模仿当年苹果那支“Mac 对比 PC”的广告，做了内部宣传。

## 重点五：Qodo 创始人的“有边界的 L4”

重点五，代码审查公司 Qodo 的创始人，写了一篇长文。为什么重要？因为它给“AI 写软件到底走到哪一步了”，提供了一把尺子。

他的核心观点是：每个开发环节都有 agent 参与，不等于你就有了软件工厂。

他仿照自动驾驶，给 AI 开发分了级。L二，是 agent 干大块活，人在旁边盯着。L三，是在限定条件下，agent 能跑完整个交付流程，但人还得随时批准，或者救场。L四，是关键的一级：对某一类边界清楚的改动，agent 能自己走完验证、发布，出了问题还能安全回退，不需要人及时赶到。

他强调，边界本身就是能力的一部分。成熟内部服务的例行改动，可以冲 L四；涉及支付这类事情，仍然要人牢牢把着。

还有一句很实用：再开一个 agent 叫它“审查员”，不等于有了独立验证。验证必须真正独立于写代码的那一方，不能被“生成的一方”牵着走。放行要靠证据，而不是靠 agent 自己的信心。

至于怎么衡量，他说，要看合格的活干完了多少、还剩多少人工、出错的代价有多大，而不是看用了几个 agent、生成了多少行代码。他的口号是：系统大于 agent，agent 大于模型。而且这套系统，团队要自己建、自己拥有。

## 重点六：Claude 工程负责人谈怎么用 AI

重点六，跟着上一条一起听。Claude 的工程负责人 Felix 接受访谈，讲他们团队自己怎么用 AI。为什么重要？因为做模型的人怎么用模型，比大多数教程都有参考价值。

他说，团队大约一周半，就做出了 Claude Cowork 这个产品。

他的第一个观点：别当传送带。不要自己挑一条崩溃报告丢给模型，而是让模型直接看全部的崩溃数据，自己决定先修什么。

第二，他觉得行业对“让 agent 扮演角色”用力过猛，大多数任务他根本不设人设。所谓的技能包，他也劝大家慎用，说过时得很快，有时候删掉，效果反而更好。

第三，防幻觉。他的办法是对抗评审：同一份产出，开几条线程，专门去证明它是错的；再开一条线程当裁判，判断哪些批评站得住。他最不信的，是让同一个对话给自己打分。

最后他说，今天的 AI 产品，大概还处在智能手机出现之前的功能机阶段。给工程师的建议是：去证明你的共情能力，和把多个系统整合起来的能力。只会背某一个接口的用法，会越来越不值钱。

把重点五和重点六放在一起，其实是同一个意思：别只盯着模型，系统怎么设计、边界怎么画、验证怎么做，才决定 agent 能走多远。

## 重点七：被遗忘的 Jupyter 标签页

最后，重点七，留给 Jupyter。为什么重要？因为这是 notebook 平台最实在的一笔账。

Bluesky 上一位专门做集群审计的工程师说，他查过的每一个共享机器学习集群里，分出去的 GPU 时间，有三分之一到一半是闲着的。

为什么平时看不出来？因为大家盯的是 CPU 使用率面板，而跑 GPU 的任务几乎不申请 CPU。他打了个比方：午饭时开着没关的一个 Jupyter 标签页，就等于占着一整块高端显卡，每小时大约四美元。

这正是 JupyterHub 里“闲置回收”要解决的问题，也就是把一段时间没有动静的会话自动关掉，把资源还回去。

如果你在管团队的 notebook 平台，今天就可以去看一眼：闲置回收开了没有，超时设的是多久。

顺带一条 Jupyter 相关的：做 Claude Code 模板的开发者 Daniel Avila，把学习 Anthropic 托管 agent 的过程，做成了一组按顺序运行的 notebook。notebook 当可执行教程，这又是一个例子。

## 评论一：朴素检索打败复杂记忆

接下来是评论与讨论。五条消息，我们会讲清楚原帖说了什么，也会明确说出我们自己的判断。

第一条，也是我们觉得今天最有价值的一条：最朴素的检索，打败了复杂的 agent 记忆。

一篇新论文测了一个最朴素的 RAG 方法。RAG 是检索增强生成，就是先从资料里找出相关片段，再交给模型回答。论文里这个版本简单到近乎偷懒：不做摘要，不抽取事实，不建知识图谱，只把原始对话切成小段存起来，用的时候检索出来，再排一遍序。

这里的排序这一步很关键。论文做了拆解实验：去掉重新排序，成绩明显下降；只给模型一条证据，掉得更多。反过来，往里加事实抽取、加摘要、加图谱，都没能超过最朴素的版本。

结果，在四个长对话记忆测试里，七组对比它赢了六组。准备数据的时间，它不到半小时；一些主流的记忆系统，要好几个小时，最长的超过一天。

论文还有一个更扎心的发现：他们审计了一个流行的记忆系统，发现“更新”和“删除”这两类操作，只占全部写入的很小一部分；把这两项关掉，准确率反而还涨了一点。作者的解释是，把历史改写成记忆条目，会丢掉回答问题需要的那些关系。

复杂的记忆系统听起来更聪明，也更好讲故事。但这篇论文提醒我们，该由评测来当裁判。

我们的判断是：对大多数团队来说，在上任何记忆系统之前，都应该先把“原文加检索加重排”当基线跑一遍。保留原始证据，比只保存加工后的摘要更可靠，这本来就是做知识系统的老原则。

最有力的反对意见，论文自己也承认：它只测了公开的离线数据，而保存原文，会带来隐私和删除的实际成本。这一点我们同意。但这说明要认真设计怎么删，而不是说明一定要先把原文改写掉。

给你一个具体建议：这周拿你们自己的一批历史对话，跑一个最朴素的检索基线，和现有的记忆系统比一比。差距如果不大，复杂度就该砍掉。

## 评论二：Netflix 的本体知识图谱

第二条，Netflix 把可观测性做成了本体知识图谱。

先感受一下规模。Netflix 转播 Jake Paul 对 Tyson 那场拳赛时，同时在线的播放流大约有六千五百万。在这种系统里，有一次首页渲染变慢，排查花了大约四个小时。但大部分时间不是在解难题，而是在重建各个系统本来就知道、却从没写下来的关系：哪个服务归谁管，哪次发布改了什么，哪个实验影响了哪部分用户。

他们的判断是：这本质上是个数据建模问题。于是用一整套语义网标准，搭了一个运维领域的本体。本体，你可以理解为一份严格定义的“概念和关系的词典”。他们连 Slack 里事故讨论时提过的假设、被否定的思路，都存成了结构化的记录。大模型给出的模糊结论，必须符合本体里的类型约束，才能写进去。

最后的效果，是一个自动找根因的系统：几个各管一摊的 agent，用同一套词汇协作，给出的是带证据的猜想，而不是结论。告警照响，人照样拍板。省下来的，是找负责人、翻发布记录、跨系统对线索的那几个小时。

我们的判断是：这篇值得读，但最该借鉴的不是那套技术栈，而是两条原则。第一，把各个系统心照不宣的关系写下来，让它能被查询。第二，大模型的输出，要落到有约束的结构里，而不是直接当结论。

有人会说，这太重了，只有 Netflix 这个体量扛得住。这话有道理。但 Netflix 自己总结的第一条原则，就很轻：先把“谁是谁、谁负责什么”的权威目录建起来。这件事，十个人的团队也能做。

所以我们的建议是：下次事故复盘时，记一下排查时间里，有多少花在了“拼关系”上。如果超过一半，你需要的可能不是更好的告警，而是一份能查询的服务目录。

## 评论三：开放科学遇上“科学国家化”

第三条，换个方向，聊开放科学。

学术出版机构 Frontiers 旗下的政策实验室，发了一篇评论。文章的意思是：AI 越来越被各国当成首要的战略资产，和民族主义的政治议程绑在了一起。各国的重心，从全球合作，转向国家竞争。

作者搬出了社会学家默顿当年总结的科学规范，比如知识公有、标准普遍，并借用经济学家 Paul David 的说法，把其中一条扩展成“开放”。他们的结论是：科学体系很脆弱，很容易退回到各国互相隔离的状态。

作者说，科学产出从来没有像今天这样在地理上分散，国际合作却从来没有像今天这样受地缘竞争的约束。他们举的例子是：监督美国国家科学基金会的国家科学委员会，最近被解散了，拟由有权批准或终止资助的政治任命人员接手。

我们的判断是：这篇文章点出了一个真实的矛盾。AI 能走到今天，靠的是几十年公开的论文、数据和开源代码。为了争 AI，把科学往封闭里推，等于在拆自己脚下的台阶。

当然，最强的反驳是：科学从来没有完全脱离国家利益，涉及安全的研究，一直都有保留。这一点我们承认。但区别在于，过去是少数领域例外，现在的风险，是把“例外”变成默认。

对听众来说，能做的事情其实很具体：你手上能公开的数据和代码，放到长期存档的公共仓库里，而不只是留在个人网盘或者实验室服务器上。开放，最终是靠一个一个这样的动作撑起来的。

同一天，德国亥姆霍兹联合会的开放科学办公室也发了一个声明，替科研图书馆说话。里面有一句话很适合放在这里：在这里省钱，就是在科学主权上省钱。

## 评论四：AIPOCH 的 .science 研究包

第四条，和 Jupyter 社区关系很近。

一家叫 AIPOCH 的公司，开源了一个 AI 研究工作台。核心是一种研究包，他们就叫它“科学包”。它要解决的问题很具体：接手同事的分析时，对话记录、数据、代码和运行结果散在各处，拼不起来。

这个包会把这些东西和它们之间的关系打在一起。拿到的人，可以只读地复查，也可以从某一步分叉，接着往下做。它的格式参考了一个叫 RO-Crate 的研究对象标准。安全上有两个默认：导入的时候不会自动执行代码，原作者的访问凭据也不会被恢复。

我们的看法是：方向是对的。当 AI 对话已经成了研究过程的一部分，复现一项研究，就不能只看最后的代码。而“导入时不自动跑代码”这条默认，notebook 生态很值得借鉴。

但要提醒一句：我们目前看到的，是一篇媒体报道加一篇预印本，还没有看到真实用户的使用反馈。是不是好用，还得等。另外，公司的 CEO 说，“氛围式研究”的时代要来了。这个说法我们有保留：研究最怕的就是只凭感觉。好在这个工具做的事情恰恰相反，是把过程留痕。

如果你在用 notebook 加 Binder 做可复现研究，可以想想：你的项目里，AI 参与的那部分过程，现在被记录下来了吗？

## 评论五：Thariq 离开 Anthropic

最后一条，Thariq 离开 Anthropic。这条我们说得克制一些。

事实是这样的。Thariq 发文说，他在 Claude Code 上工作了一年多，看着它的规模远远超出自己的想象，现在决定离开。他说自己仍然深信公司的使命，同事是他见过最有才华、最认真的一群人。接下来，他会先休息一阵，再开始新的事情。

中文圈一开始有个误会。AI 博主归藏最初转述时，把 Thariq 称作 Claude Code 的作者，随后自己更正了：作者是 Boris Cherny，也是现在整条产品线的负责人。Thariq 的影响力主要在社区，他是 Anthropic 在 X 上和开发者打交道最多的面孔之一，写过很多关于技能、agent 开发包和上下文的内容。

至于他为什么离开，原帖没有说，我们也不猜。

我们想说的只有一点：连中文圈很有影响力的博主，一开始都把作者弄错了。这说明，大家对“谁在做这个产品”的印象，很大程度来自谁在社交媒体上说话最多。

所以一个实在的建议：如果你依赖 Claude Code，除了关注个人，也关注一下官方的开发者账号。Thariq 自己在告别帖里，也推荐了几位同事和官方账号。
