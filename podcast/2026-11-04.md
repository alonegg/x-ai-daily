# 11 月 4 日 AI 播报

## 开场与头条预告

早上好，今天是十一月四号，星期三。这里是 X 每日 AI 播报，接下来二十多分钟，我们把昨天 AI 圈的事情过一遍。

先说今天最重要的三件事。

第一件，OpenAI 公布了自己重做的代码仓库后端。原因很直接：AI 写代码太快，公司原来的 Git 服务器扛不住了。上个月 Anthropic 也碰到同样的问题，但两家走了相反的路。

第二件，一家欧洲金融科技公司据说把两千名工程师，从最贵的闭源模型换到了自己部署的开放模型，成本只剩十分之一左右。

第三件，开放科学领域用了十几年的一个平台 OSF，定下了关停时间表，这个月中旬起就不能再建新项目了。

另外，评论环节还会聊一篇很实在的论文：让 AI 编程助手干完活自己复盘、自己改工作手册，到底管不管用。

## 快讯

下面是快讯。后面重点和评论要细讲的，这里先跳过，只说其余的新鲜事。

谷歌那边，有评测者在竞技场上试了 Gemini 四 Carbon，说做三维和网页设计还不如 Claude 的 Opus，但已经非常接近。

再看模型和论文。腾讯混元发布了科研智能体系统 Hyra 二点零，说它能自己设计方案、写代码、训模型，做出了蛋白质设计模型和数学证明流程。这些成果都是官方自己说的，系统也没有开源。

微信视觉团队开源了一个小模型，二十亿和四十亿参数两个版本，能找物体、数数、认字、抠图，一个模型全包。它有个难得的优点：图里没有你要找的东西，它会老实说没有，而不是硬框一个出来。

一个二百七十亿参数的电脑操作智能体，叫 CUA-Master，在操作系统任务测试上拿到八十分出头，作者说能比肩大得多的闭源模型。

再说 agent 工程。Claude Code 团队的 Addy Osmani 写了一篇长文，提醒大家：模型越强、输出越像样，人就越容易不再多看一眼。他的建议是，动手前先自己立一个假设，先看它跑了什么命令、输出了什么，再看它的总结。

关于检索，有两篇论文都在说同一件事：检索好不好，先取决于 agent 会不会自己查、自己读、自己调整，其次才是索引做得多复杂。其中一篇只用最朴素的关键词搜索，配上会自主探索的 agent，在两个难的问答测试上分别做到了八成五和九成一的准确率。

英伟达开源了一个叫 Auto Ontology 的项目。本体，就是给企业里的指标和概念下严格定义的一套知识结构。它把这层含义交给 agent，让它查数据时先搞清楚收入到底指什么，再写查询语句。

LangChain 讲了他们怎么设计让 agent 操作浏览器的工具。创始人的说法是，浏览器正在变成新的终端。

然后是做东西的人。独立开发者 levelsio 前天把经典游戏《战地一九四二》搬上了网页，昨天又加了一张有飞机的地图，还把服务器登记成了官方服务器，原版客户端也能连进来。

## 重点一：Anthropic 开源 FlashProve

为什么重要？因为现在你拿到一条 AI 的回答，其实没法确认它真的来自对方宣称的那个模型。

Anthropic 昨天发布了一项研究，叫 FlashProve，做的是可证明推理。意思是，用密码学的方法给每次回答附上一份证明，让人可以验证这条回答确实出自某个指定的模型。官方说它比之前的开源方法高效得多，代码也开源了。

官方举了两个用途。一是让攻击者更难劫持一段对话。二是让做安全评测的机构确认，自己测的模型，和真正卖给客户的是同一个。

一位中文 AI 博主的解读补充了细节：它用的是零知识证明，也就是能证明一件事成立、却不泄露背后秘密的技术。用户不需要拿到模型权重，用普通电脑几秒钟就能核对，厂商的参数也不会外泄。他特别提到，这对用第三方中转服务的人有意义，可以确认回答没有被偷偷换成便宜的模型。

我们的看法是：这是一项研究原型，离各家真正部署还有距离。但方向很重要，当越来越多的决策交给模型，能验证是谁在回答，会和能看懂回答一样重要。

## 重点二：Claude 插件登录即连，Claude Code 十月更新

为什么重要？因为在公司里用 AI 助手，最烦的往往不是模型不够聪明，而是一个个工具都要单独授权。

先解释一下。插件就是让 Claude 能直接操作别的软件的扩展，比如读 Notion 文档、查监控数据，背后通常连着一个 MCP 服务器。MCP 是模型上下文协议，一套让 AI 对接外部软件的公开标准。

以前每连一个插件，员工都要跳到那个软件登录，再点一次允许。公司用十几个工具，就要重复十几次。现在 Claude 的团队版和企业版有两种新办法。一种是通过公司统一的账号系统，管理员一次给全公司开通。另一种是，如果公司的账号系统还不支持，就由 Claude 直接替已登录的员工担保身份。目前支持十四家插件，包括 Notion、Figma 和 Linear。个人版暂时不在范围内。

同一天，Claude Code 公布了十月的更新汇总。几个实用的点：长时间闲置的会话，会在缓存过期前自动压缩，回来时更省额度。在消息里写一个词 ultrathink，可以只让这一轮多想一想。超时的命令不再被直接掐断，而是转到后台继续跑。还有，最贵的几档订阅现在每月附带一笔接口额度。

我们的看法是：模型能力之外，真正决定 agent 能不能在公司里铺开的，是授权、额度和权限这些不起眼的工程细节。

## 重点三：模型改模型的权重，被独立复现了

为什么重要？因为前天那项权重空间编程的研究，最大的疑问就是能不能复现。

先回顾一下：麻省理工的研究者让 GPT 六 Astra 直接改一个小模型的权重，也就是模型内部的那些数字，不训练、不算梯度，小模型的数学成绩从不到一成涨到了将近五成。

昨天有两个新进展。第一，一位谷歌研究员复现了原文里的一个实验：让模型一次写出一个能玩打砖块游戏的小网络的全部权重。他把好几代模型都测了一遍，发现上一代模型基本做不到，到最新一批前沿模型才突然跳到原来水平的二十倍左右。他说，这是一种刚刚出现的台阶式新能力。

但他也特别强调，被改的网络只有两万个参数左右，而前沿大模型是万亿级，不能因此说大模型已经能改自己。

第二，程序员 Simon Willison 在自己的笔记本上，用一个开放权重的千问模型试了一下，花了四十五分钟以上，也做到了同样的事。

还有一个细节值得记住。原文作者自己说，换成一个本来就很少陷入循环的小模型，同样的方法没有带来提升。他们的结论是，改权重能去掉挡住能力的障碍，但加不出模型本来没有的能力。

我们的看法是：这件事从一篇博客，变成了有独立复现、有跨代对比的研究方向，可信度上了一个台阶。但离模型改进自己，还隔着好几个数量级。

## 重点四：agent 可能很快只剩一个工具

为什么重要？因为过去两年做 agent，核心工作就是设计一大堆工具，而这个做法可能正在被推翻。

一位 AI 工程师写了篇文章，讲一个趋势，叫 Code Mode，代码模式。传统做法是，模型每一轮只调用一个工具，等结果回来再想下一步。代码模式是，只给模型一个工具：执行代码。模型写一小段脚本，在隔离的沙箱里，把查询、筛选、修改、并行这些动作一次做完，中间结果大多不用塞回模型的上下文里。

他认为，用 Python 或 JavaScript 这种有类型的沙箱，比只给一个命令行好：函数直接对应接口，出错能捕获，截图也能直接交给下一轮。文中提到一家公司把自己的编程 agent 切到代码模式以后，终端编程测试的准确率涨了三个多点，模型花费降了一成五左右。

他也留了余地：不是每个 agent 都真会只剩一个工具，很多为人类和命令行设计的工具，接过来未必顺手。

我们的看法是：这和今天评论里的 Git 那条是一个方向，agent 越来越像程序员，而不是一个点按钮的助手。给它的接口，也应该越来越像给程序员的。

## 重点五：独立开发者用 AI 把开支砍掉九成

为什么重要？因为大家都在谈 AI 帮人多做事，这是一个 AI 帮人少花钱的具体账本。

levelsio 说，他所有网站和应用加起来，一年服务两万个付费用户、两亿多访客，现在的业务开支只要每个月三百美元左右。这里没算他那个 AI 照片产品单独的显卡费用。

他说 Claude Code 帮他每月省下了将近三万四千美元。最大的一笔，是给照片产品换了更好也更便宜的视频模型，显卡账单从每月三万六千降到了七千。

还有几笔很有意思。他的服务器备份原本无限期保留所有历史版本，十多年下来一直在交钱，改成只保留三十天后，账单从一千二百美元降到了二十六美元。Claude 还检查了他自己的 Claude 订阅，发现他根本用不满最高档，于是降了一档。

他说，算上照片产品，开支比去年降了九成。他的看法是，AI 特别擅长自己找到省钱的地方，短期对经济不一定是好事，长期会砍掉冗余。

我们的看法是：这里面没有一项是高深技术，全是没人去看的账单。AI 的价值，在于它愿意把这些枯燥的东西一条条看完。

## 重点六：面向科研的开放权重模型

为什么重要？因为科研需要检查、修改和复现，闭源模型给不了这些。

昨天有一个团队发布了 Hydrogen 一点零，说是第一个面向科学研究的开放权重模型。开放权重，就是把训练好的模型文件公开，任何人都能下载、检查和改造。它是在智谱的 GLM 五点三上，用团队内部的科学数据、实验记录和发现过程再训练出来的。

他们公布的成绩是，在一个前沿科研测试上得了百分之三十八点三，高于他们给出的 GPT 六 Astra 的成绩。他们的理由很直白：科学应该开放、协作，只有开放权重，研究者才能检查和在上面继续建设。

同一天还有几个开放模型：一个把视频模型改造成图像模型的开源项目，生成速度快了五倍；还有图灵奖得主 Yann LeCun 转发的一个视觉模型，用少得多的算力和数据，追平了更大的前作。

我们的看法是：分数都是团队自己报的，要等第三方复测。但科研开放模型这条线，和今天评论里 OSF 关停的消息放在一起看，很值得开放科学圈的人关注。

## 一起讨论

下面进入评论环节。每一条，我们会讲清楚原帖说了什么，也会明确说出我们自己的判断。

## 评论一：Git 撑不住 agent，是改造还是替换

先讲一个对比鲜明的案例。

Git 是程序员管理代码版本的工具，每次改动存成一个提交，推到公司服务器，同事再拉下来。OpenAI 和 Anthropic 都把全公司的代码放在一个大仓库里，而 AI agent 写代码太快，这个仓库成了瓶颈。

数字很惊人。以两年前为基准，OpenAI 合入主线的提交数，今年第三季度涨到了近十五倍。Anthropic 每天合入的改动，从五月的两千五百个左右，到九月超过了三万个。OpenAI 说，去年年底开始，推拉代码都变慢，合并经常失败。

两家的解法正好相反。OpenAI 选择改造：工程师和 agent 照常用 Git，只把服务器换成自研的 Pando。每个分支各管各的，推不同分支互不等待。推送的等待时间缩短了大约八成，每天分发将近一千个 TB 的数据。修的问题，有几项已经回馈给了 Git 官方。

Anthropic 选择替换：上个月公布的 Scion 有自己的客户端和服务器，提交直接在服务器上生成，缺哪个文件就取哪个文件。服务器占用只有原来的两百分之一。

还有一个共同点：两套系统主要都是 AI 写的。Pando 从立项到上线十周，代码主要由 agent 写。

我们的判断是：瓶颈正在从写代码，转移到代码写完之后的所有环节，存储、测试、合并、审查。Anthropic 自己预计，未来半年到一年，这类问题会在更多公司出现。如果你的团队用 GitHub 或者 GitLab，OpenAI 这条路离你更近，因为改进会直接进 Git，工具不用换。

给你一个具体建议：这周看一眼你们的持续集成，也就是每次改动后自动构建和测试的流程，平均要等多久。如果 agent 用得越来越多，这个数字会是最先告警的地方。

## 评论二：前沿模型变成例外，开放模型变成默认

这一条有争议，我们正反两面都说。

原帖说的是：据一位转述者引用这家公司 AI 运营负责人的话，欧洲金融科技公司 Revolut 把大约两千名工程师迁到了自己部署的智谱 GLM 模型上写代码，Claude Code 和 Codex 变成了例外名单。他们用了五十六块英伟达的高端显卡，每百万 token 的综合成本大约三毛美元，差不多是原来付给两家闭源厂商的十分之一，工程交付周期改善了七成。

最有意思的是这一句：收益出现在不再给 token 定量之后。工程师不再把 AI 省着留给难题，而是什么都拿它来做。

另一位投资人补充说，据报道，一家客服 AI 公司九成左右的工作负载跑在开放模型上。他的判断是，新场景先用最聪明的模型，流程一旦成熟、可预测，更小更快的专用模型会胜出。

我们的判断是：方向大概率是对的，成本和速度在大规模使用时确实压倒一切。但最有力的反对意见也要说清楚：这些数字来自转述，我们没看到 Revolut 的官方材料；交付周期改善七成，也很难全算到换模型头上，因为同时变的还有用量。

还有一点值得注意：转述者说，这对每一家准备上市的实验室都是定价难题。这句话是他的观点，不是事实。

给你一个具体建议：如果你在团队里管 AI 预算，先别急着换模型，先统计一下，大家是不是因为额度紧，把 AI 只用在了少数任务上。不再定量，可能比换哪个模型影响更大。

## 评论三：维护者失去的，是对面的人

这一条我们按现场报道的方式来讲，主要讲事实。

科学开源组织 pyOpenSci，在欧洲最大的 Python 会议上办了一场焦点小组。十五位核心科学 Python 和 Linux 项目的维护者，聊了两个多小时。

他们本以为会听到审查 AI 代码太花时间。结果谈话一次次回到另一件事：人和人之间的联系没了。维护者的乐趣，在于帮一个新人把修复合并进去，顺便带他成长。现在，有 agent 账号批量提交改动，只为了刷贡献记录。

大家提到三种情况。第一，不知道对面是谁。有维护者怀疑一个贡献者是机器人，追问之后发现是真人，对方说，这是我昨晚自己写的。两边都很尴尬。第二，贡献者带着 AI 觉得自己什么都能做，根本不和维护者交流，维护者被当成了基础设施，而不是人。第三，动机变了，有人为了简历或者绕过招聘筛选去刷改动。

也有人反对把低质量的提交一律叫作 AI 垃圾。他们说，真正的问题是，对方愿不愿意花心思和项目交流。

最一致的结论是：全面禁止 AI 是错的，这只会让人藏起来不说。他们更倾向的做法是：先开一个讨论，再提改动；说明是否用了 AI；质量标准不变。有人甚至请贡献者来开一次会，证明自己是真人，但这又和多年来降低参与门槛的努力相冲突。

我们的判断是：这件事对 Jupyter 这类科研开源项目特别要紧，因为维护者本来就少，带新人的链条一断，很难接上。

给你一个具体建议：如果你维护一个项目，可以在贡献指南里加一句，提改动之前先开一个议题聊几句。这是成本最低、也最像人的一道门。

## 评论四：OSF 关停的时间表

这一条我们先把时间线讲清楚，再说怎么办。

OSF 是开放科学框架，很多研究者用它存放研究计划、数据和材料，已经用了十几年。运营它的开放科学中心在公告里写得很清楚，昨天又被研究者们广泛转发：从这个月十六号起，不能再在 OSF 上新建项目；明年二月十九号以后，所有项目，不管公开还是私有，都变成只读。

哪些不受影响？已经公开的项目会长期保留，链接和论文标识符继续有效。预注册和预印本照常可用。他们还说，将来可能删除私有项目，但会提前十二个月通知。

原因是钱。公告写道，要维持现在这样全面的 OSF，未来几年每年需要四百万到五百万美元，在当前的资金环境下筹不到。以后 OSF 只专注研究计划、预注册和预印本，数据和代码交给其他专门的仓库，比如欧洲核子研究中心托管的 Zenodo。

我们的判断是：这是开放科学基础设施可持续性问题的一个缩影。一个平台包办一切的模式撑不下去，接下来要靠多个能互相连接的服务分工。好处是各自专精，代价是研究者要多管几个地方。

给你一个具体建议：如果你或者你的课题组有私有的 OSF 项目，这周就列个清单，能公开的考虑公开，不能公开的在二月前搬走。做系统综述的，尤其要检查表格和数据是不是放在项目里。

## 评论五：让 AI 自己复盘、自己改手册，管用吗

最后一条，我们拆一篇论文。

先说背景。很多人用一种复盘技能：AI 编程助手干完一个任务，回头看哪里卡住了，再提议修改项目里的工作手册，下次就不再走弯路。听起来很美。

新加坡和德国的两位研究者专门测了这件事。他们从一个真实代码修复的测试集里挑了三十个问题，让 Claude Code 每修完一个就复盘一次，一共得到一百二十五条建议。大多数建议确实针对任务里真实发生的事，但也有十几条是不管发生什么都会提的，比如加格式检查。

关键结果是：能拿来测的改动里，真正在原设置下碰到目标问题的只有七次，其中只有两项彻底解决了问题。一项是在手册里写明这个项目用什么命令跑测试，误用的次数从五次降到零。另一项是列出一份本来就会失败的测试清单。

更值得警惕的是副作用。有一份清单写着，不在清单里的失败都当成是你造成的。结果在一个无关任务上，AI 多做了很多检查，用时从一分多钟涨到了四分钟左右。

作者的结论很实用：跑测试用什么命令，这类全项目通用的信息，记下来一直有用；哪几个测试会失败，这类和环境有关的信息，换个任务就可能对不上。他们也承认样本小，每种设置只跑了五次。

我们的判断是：自我进化的前提是有明确的验收标准。没有标准，复盘只是把更多规矩堆进手册，规矩越多，agent 越慢。

给你一个具体建议：打开你项目里给 AI 看的那份说明文件，把条目分成两类，通用的留下，和某次任务有关的删掉或者标上日期，过一阵再检查还对不对。
