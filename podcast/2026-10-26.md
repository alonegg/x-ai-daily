## 重点一：AI 审计服务器与 Tailscale 漏洞

接下来是今天的重点，一共七件。

重点一，AI 时代的服务器安全。为什么重要？因为攻击已经开始用上 AI，独立开发者和小团队，必须用同样的工具来守。

一位知名独立开发者说，他昨天花了一整天，在每一台服务器、每一个网站上，对 Claude Code 输入同一句话：对这个网站和服务器，做一次完整的安全审计。

他原本就开着系统的自动安全更新。这次又让 AI 生成了组网规则，把每台服务器隔离开。这样就算一台被黑，也连不到其他服务器，更连不到他的电脑和手机。网站服务也尽量不用最高权限运行。

他引用的一条帖子更吓人：另一位创业者说，自己的一家公司遭到了前所未见的 AI 网络攻击，压力大到怀疑自己中风，进了急诊。

于是他提议，每个月专门留出一个“安全周”。他的理由是：模型越强，预防性的防御也得跟上；好在 AI 的攻防能力，目前看起来大致相当。

讽刺的是，几个小时之后，他转发了一条新闻：“这回轮到 Tailscale 了。”Tailscale 是很多人用来组建私有网络的工具。一份安全报告说，它的远程登录功能有缺陷，黑客可能从一台被攻破的设备，拿到其他服务器的最高权限。报告一共列了十一项发现，分成五组。

我们的看法是：组网工具本身，也是攻击面。把服务器藏进私有网络是好习惯，但前提是这个网络工具本身要及时更新。这份报告的细节目前来自安全媒体的转述，建议直接看 Tailscale 官方的公告。

## 重点二：Agents SDK 的额度 bug

重点二，Anthropic 的 agent 开发包有计费 bug。为什么重要？因为越来越多的第三方编程工具，底层用的就是这个开发包，用户可能在不知情的情况下多花了额度。

起因是一位用户求助：他刚装上一款叫 T3 Code 的编程工具，用 Claude 最贵的 Max 套餐，只开了一个会话修几个 bug，大约半小时，五小时的额度就用光了。

T3 Code 的作者 Theo 花了很多时间排查，最后确认，这是 Anthropic 那边的真 bug：所有经过这个开发包的用量，消耗五小时额度都比直接用 Claude Code 更快。好消息是，周额度不受影响。他已经把问题报给了 Anthropic。

他的推测是：Anthropic 前段时间提高了几档套餐的五小时额度，但可能忘了把这次提升，也应用到开发包上。他找到的一个 GitHub 问题，恰好在那次调整几天后就被提了出来，所以他说自己有九成五的把握。

我们的看法是：“确认是 bug”这个结论来自 Theo，他本人也是 T3 Code 的作者，有利益相关；原因目前还是他的推测。Anthropic 官方怎么回应，值得等一等。如果你最近觉得额度掉得特别快，可以先对照一下，是不是在用基于这个开发包的工具。

## 重点三：Hugging Face 的 DNA 模型

重点三，Hugging Face 的 DNA 模型 Carbon-X，有了更完整的数字。为什么重要？因为它代表了一种思路：用开源的小模型，在专业领域里接近闭源旗舰，而成本低几个数量级。

前几天它刚发布。昨天，一家 AI 媒体做了完整的拆解，Hugging Face 的创始人也转发了。

它的设计很简洁：一个模型同时读 DNA 和文字，没有单独的 DNA 模块。DNA 序列每六个碱基切成一个单位，从阿里的千问模型出发，再用三千多亿个单位的 DNA 和文本继续训练。

成绩方面，五项 DNA 测试平均下来，它在不开思考的情况下，和 OpenAI 旗舰模型开到最高推理档的成绩，只差不到一分。

但它也有明显短板。比如判断基因剪接位点的题目，它只答对了三成左右，而且没有经过临床验证。

最直观的是成本。给两百多万个已知的基因变异打分，Hugging Face 估计用它大约三百美元；换成前沿的闭源模型，要贵上百倍，甚至上万倍。

我们的看法是：开放权重加上一张显卡就能跑，对研究机构很有吸引力。但这些成绩都来自发布方，而且它自己也承认有短板。在医学场景里用它，一定要当研究工具，不能当诊断工具。

## 重点四：Grok Bot 连上 X Money

重点四，个人 AI 助理的信任问题。为什么重要？因为这类助理能看的东西越多，用户越在意“它有没有先问过我”。

一位知名的 AI 播客主持人发帖说，Grok Bot 最近新功能很多，打电话、做网页，这很好。但它现在出现在 X 的私信里，而且关不掉；还在他没要求的情况下，自动连上了他在 X 上的支付账户 X Money。

他的原话大意是：它应该先问我，要不要介入我在 X 上的事务，而不是突然跳出来说，“我能看到你的资金往来了”。他说，这正是个人助理失去用户信任的方式。

他引用了另一位用户的遭遇：同样是没经同意就连上了 X Money，而且弹窗里的撤销按钮还不起作用，只能自己翻设置去关。

同一天，也有正面评价。AI 博主归藏说，Grok Bot 的问题反馈做得很好：你在聊天里发现 bug，它会主动问你要不要反馈，然后直接把日志和问题描述发给团队。

宝玉的观察更冷静：个人 agent 让很多老板着迷，但对天天用编程 agent 的人来说，其实没什么太大波澜。

我们的看法是：对能碰到钱的功能，默认应该是关闭，由用户主动打开。功能上得再快，授权这一步也不能省。

## 重点五：Block 的全双工语音模型

重点五，Block 的语音模型 Dessa。为什么重要？因为它走了一条和主流不同的路：完全不经过文字。

Block 是 Twitter 联合创始人 Jack Dorsey 的公司。一位中文技术博主昨天做了详细整理。

现在大多数语音助手的做法是：先把你的话转成文字，交给大模型，再把回答念出来。Block 的团队认为，这样会丢掉语气、讽刺、叹气和哽咽。更严重的是安全问题：一个人在剧痛中说话，系统可能完全察觉不到，还在照常应答。

所以 Dessa 只用人类的对话声音从零训练，没有文字，也没有现成的底座模型。它是全双工的，也就是能边听边说，会插话，也会“嗯”“好的”地附和。团队说，它能在高配的 MacBook 上本地实时运行，整个模型只用一台英伟达的服务器机柜就训练出来了。

演示里，它会在句子中间笑出来，你让它大声它就大声，还能接上你一时想不起的电影名。

我们的看法是：“听得出情绪”这个方向很有意义。但目前我们看到的，都是团队自己发布的演示录音，还要等更多人真正上手。

## 重点六：Theo 的一个月清单

重点六，一个开发者一个月能做多少事。为什么重要？因为它让我们直观看到，最强的编程模型，正在怎样改变一个人的产出。

有人说，Claude 的旗舰模型 Opus 五点五发布一个多月了，还没人用它做出什么像样的东西。这话其实是 Theo 自己发的反讽帖。随后，他列了一张清单。

他说，这一个月里，他用 Rust 完整重写了 TypeScript 的编译器，比官方的 Go 语言版本还快三倍；做了一个 Rust 子集的工具链；还有一个模型对比网站，和一个给 agent 用的操作系统雏形，已经有五台机器在跑。

自家产品上，他把搜索的准确度提高了几倍；让 agent 在等待测试和评审时自动休眠，调用 GitHub 接口的次数减少了九成；还删掉了一半以上的测试。另外，还有大约三百七十个已合并的代码提交。他的结论是：“这个月挺慢的。”

同一天，他还说了一句很冲的话：如果你还在手动合并大部分代码提交，你已经落后了。

我们的看法是：这份清单真实地展示了 AI 编程的上限，但也要看到，Theo 是全职做 AI 编程工具的人，有大量时间和算力。“手动合并就落后”这句话，对有严格审查要求的团队，未必适用。

## 重点七：用 AI 做历史视频

重点七，换个轻松一点的话题：用 AI 做历史纪录片。为什么值得说？因为它展示了一种新的内容生产方式：一个人加一段提示词，就能把档案馆里的原始录像，做成带双语字幕、分章节的纪录片。

中文技术博主宝玉，根据一位网友的线索，找到了美国帕萨迪纳市政府存档的一段录像。二零零三年三月，一个穿灰色 T 恤的大学生走到话筒前说：“我叫 Dario Amodei，是加州理工学院的大二学生。”他带来一份反对伊拉克战争的请愿书，当时已经有将近六百名师生签名。

请愿书里有一句话：我们创造推动这个国家前进的技术，看到它被不加区分地用于战争，深感痛心。十天后，伊拉克战争爆发。十八年后，他和几位前 OpenAI 同事创办了 Anthropic。

宝玉给录像配了中英双语字幕，还做了一条宋美龄一九四三年在美国国会演讲的视频，用的是美国国家档案馆保存的二十一分钟原声。他特别说明，中文译文由 AI 辅助翻译，没有经过人工校对，以录音为准。有网友嫌“AI 味太浓”，他回应说，设计是模型自己出的，有设计品味的人可以做得更好看。

我们的看法是：这类视频的价值，在于把原始档案带到更多人面前。但标注清楚哪些是原声、哪些是 AI 翻译和示意图，是基本的诚信。宝玉在这一点上做得很规范，值得参考。

## 评论一：主循环加技能包

接下来是评论与讨论。五条消息，我们会讲清楚原帖说了什么，也会明确说出我们自己的判断。

第一条，用拆解的方式来讲：Claude 博客这篇关于 agent 架构的文章。

先说它反对什么。很多大企业做 agent，是每个团队先做一个自己的子 agent，平台再在上面盖一层总调度。看起来分工清楚，实际问题一堆：在 agent 之间来回传话，细节越丢越多；每个人都往系统提示里加一句，规则互相打架；各团队只优化自己那一块，没人对整体效果负责。文章说，这往往只是在复制公司的组织架构。

再说它主张什么。一个模型，一个上下文，一个开放的工具循环。领域知识做成技能包，需要时才加载；工具也是先看简短描述，用到再展开。有一家客户做过对比，单循环比多 agent 的方案快了一倍左右。

最后说它承认的例外。上下文真的撑爆了，任务需要并行，或者一个 agent 实在选不好工具，这时候再拆子 agent。

我们的判断是：这篇文章最有价值的，不是“单循环更好”这个结论，而是它的迁移方法：先建一套端到端的评测，哪怕只有十条样例，然后一次只合并一个子 agent，看哪些任务变好、哪些变坏。文章里有个例子特别真实：合并以后速度快了，但有一个原本能过的流程悄悄断了，而且两次运行里只出现一次。

最有力的反对意见是：这是 Anthropic 自家的博客，单循环正好能多用它的强模型。这一点要记着。

给你一个具体建议：如果你们有多个 agent，这周先数一数系统提示里一共挂了多少个工具。文章说，超过三五十个以后，模型选工具就容易出错。

## 评论二：规格驱动开发的实证

第二条，换一种讲法，先抛问题：先写规格、再让 AI 写代码，到底有没有用？

这种做法叫规格驱动开发。最近 X 上吵得很凶。一位做 Claude Code 模板的开发者说，与其吵，不如看研究。他推荐了一篇卡内基梅隆大学和谷歌研究者的论文。

论文分析了两百六十六个代码仓库，访谈了二十一位开发者。三个发现。第一，接近八成的规格里，写了具体的实现细节，而不只是需求。第二，开发者普遍觉得 agent 更可靠了，但花在计划和评审上的时间也更多了。第三，研究者坦白：他们没法把规格的好处，和模型本身变强的好处区分开。

这位开发者的看法是：规格驱动开发有用，可能只是因为它逼着你想清楚自己到底要什么。

我们的判断是：我们同意这个看法，而且想补一句。做科研的人对此不陌生，这很像预注册：动手之前先写下你要验证什么。它的价值，一半在约束机器，一半在约束自己。

但第三个发现很关键。如果分不清是方法有用还是模型变强，那么“必须写规格”这条规矩，可能会随着模型进步而越来越松。

给你一个具体建议：下次让 agent 做一个中等规模的功能时，先花十分钟写一页需求，只写要什么，不写怎么做，看看结果和你平时直接下指令有什么不同。

## 评论三：手写代码的投票

第三条，正反两面都说：你现在还手写超过两成的代码吗？

Flask 的作者 Armin Ronacher，在 X、Bluesky 和 Mastodon 三个平台问了同一个问题。回答“不是”，就意味着你八成以上的代码已经交给 AI 写了。

宝玉整理了结果。X 上四千多人投票，只有一成多说“是”；Bluesky 不到一百人，四分之一左右说“是”；Mastodon 五百多人，四分之三说“是”。

Armin 自己的评价是：这次看起来没有上次那么离谱，但用户群明显是分裂的。有人质疑样本太小，他又放出了一张人数更多的更新图。

正方的解读是：AI 写代码已经成了主流，至少在 X 上的开发者里是这样。

反方的解读是：这更像是在测平台的人群。X 上聚集了大量 AI 爱好者，Mastodon 上则有很多对 AI 持保留态度的开源开发者。三个平台的样本都是自愿投票，谈不上代表性。

我们的判断是：两种解读都对，但更值得关注的是分裂本身。同一个行业，一边说手写代码已经过时，另一边还有四分之三的人在手写。这种分裂，会直接影响招聘、代码评审，甚至开源社区的协作规则。

给你一个具体建议：在自己的团队里匿名问一下同样的问题。答案可能比你想的更分散。

## 评论四：Gemini 的幻觉争议

第四条，讲一个争议，而且我们要特别小心地区分事实和观点。

事实部分：Theo 做了一个多模型评审的技能，让几个模型分别检查同一份工作。他说，Gemini 在超过八成的运行里出现幻觉。他举了一次运行的例子：在一个只有七十二行的文件里，引用了第一百七十三行；还编造了 IP 地址、命令参数和函数返回值。

观点部分：他说，这不是通常那种“谷歌稍微落后一点”，而是“放进你的技术栈就是负债”，认为它能用的工程师，不该被认真对待。

我们的判断是：他举的例子很具体，也符合不少开发者的体感。但是，八成这个数字来自他个人的工具，评测方法和样本量都没有公开，也没有对照其他模型在同一套任务上的表现。这种措辞强烈的结论，传播力很强，但证据强度有限。

更有建设性的问题是：既然任何模型都可能编造行号和参数，自动化流水线该怎么防？其实有便宜的办法：行号可以和文件实际长度对一下，函数名可以在代码里搜一下，这些都能用代码自动检查，不用靠人。

给你一个具体建议：如果你的流水线里有模型生成的引用，比如行号、文件路径、函数名，加一步自动校验，看它们是不是真的存在。

## 评论五：Swisscom 的企业知识图谱

最后一条，讲一个案例，也接着昨天 Netflix 本体的话题。

瑞士电信 Swisscom 有一百多个库存系统，每个系统只掌握一部分真相。客户、服务、供应商、合同和负责人之间怎么关联，过去要弄清楚，又慢又贵，还有风险。

他们的做法是：数据不搬家，留在各自的团队手里，作为“数据产品”对外发布；然后由一个中央的关联能力，用公司统一的数据模型作为本体，把所有东西连进一张知识图谱。数据质量在源头保证，各团队保持自治。

现在，这张图支撑着供应商合规、漏洞管理、事件管理和变更影响分析。这个案例，会在十一月十一号伦敦的一个知识图谱大会上分享。

我们的判断是：这个案例很有代表性，因为它回答了一个常见的疑问：去中心化的数据管理和统一的知识图谱，能不能共存？Swisscom 的答案是能，关键是“分散发布，统一语义”。这和开放知识体系面对的问题几乎一样：很多机构各自发布数据，靠共同的词表和标识符连起来。

不过，目前我们看到的只是大会预告，具体效果和成本还要等报告。

给你一个具体建议：如果你在做跨系统的数据整合，先别急着建大平台，先试着给几个系统共用的核心概念，写一份大家都认的定义。
