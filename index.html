    Claude 开发者账号宣布 OSS Scanner，用 Anthropic 最强的模型给关键开源项目免费、定期扫描漏洞，每个发现附带概念验证（PoC），能给补丁时也会附上。首批扫描已向维护者报告 77 个严重和 803 个高危发现（由模型评级），还在继续扫更多项目。负责人 Punit Shah 的系列帖补充：项目受 OSS-Fuzz 启发，11 天前上线，约 650 个项目申请、114 个获批，仍有 150 多个待审；curl 刚修复了 CVE-2026-92392，这是一个由早期版本 OSS Scanner 发现的高危内存安全漏洞（use-after-free），curl 作者 Daniel Stenberg 称它是 curl 很久以来最严重的漏洞之一，尽管最可能的后果是崩溃。一个意外的教训是：用邮件发送漏洞 PoC 会被邮件过滤器当成恶意软件，最初发出的报告大多被退回，现在所有报告都改为加密发送。新进展包括：试点通过 GitHub Security Advisories 交付（这是呼声最高的需求），FAQ 写清了接收标准（最常见的拒绝原因是许可证不开源，或项目不够成熟、不够关键）。

  • #Addy Osmani 拆解 Claude Code 的分层代码审查长推
    meng shao · Addy Osmani · 宝玉
    后续 （接 2026-10-19）：meng shao 详细整理了 Addy Osmani 对 Claude Code 团队审查流程的解读：Claude 写了 Claude Code 约 90% 的代码，6 月到 9 月合并的 PR 翻倍以上，回滚率反而降了 40% 多。瓶颈从写代码转向证明代码能用，审查的问题从「有没有人读过」变成「可能出什么问题、该由哪一层抓」。流水线分四层：提 PR 前 Claude 跑测试、构建和 linter 并展示真实输出，再由一个全新上下文的 subagent 独立审 diff；PR 上必需的 CI 阻塞合并，多个 AI 审查 agent 并行找 bug，由「验证者」投票过滤误报（内部 PR 获得实质评论的比例从 16% 升到 54%），另有独立的安全审查；风险由分类器而非作者判定，低风险零人工、中风险一人、高风险（计费、自动更新等）两人，AI 的批准永远不占人工名额；合并后先用 feature flag 内部灰度，每周 on-call，复盘追问「哪一层本该拦住」。两个细节：把历史上引发事故的 PR 做成每日评测集，审查器的任何改动分数不升就放弃；一个 PR 曾一夜被 AI 审了五十多轮，59% 反复标记的是旧代码，于是定下三轮封顶、只审新增 diff，一轮通过率从 65% 升到 78%。人保留方向和品味、高风险审批、架构决策和最终问责。宝玉则调侃：他那期讲「两个 AI 一个审一个改、来回 50 多轮」的视频下面，两个 AI 账号又互相评论停不下来。

    Connected Data
    Connected Data 转述 Harvey 团队 Niko Grupen 的实验：一份信贷协议常有多份草稿、修订和附函，agent 回答问题前得先确定哪个版本有效。Harvey 在 Legal Agent Bench 上让 agent 先通读客户案卷的全部文件，建一张包含当事方、日期、草稿或已签署状态、哪些版本属于同一合同的实体关系图，再对比有图和无图的表现。结果是评分标准通过率最高提升 30%，任务成本最多降低约 50%。一个找律所最近一笔担保融资并调取已签署信贷和担保协议作先例的任务里，无图时 agent 跨案卷逐个搜文件、选错先例，得 0%；有图时立刻定位，得 75%。Connected Data 也提出两个值得追问的问题：建图成本是否计入了任务成本，以及随着人们持续操作案卷，图的维护成本如何变化。
