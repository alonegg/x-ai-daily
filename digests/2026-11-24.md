## Anthropic：Claude Ship 与平台更新
- **Claude Ship（测试版）：PR 从审查、修复到批准一条龙** {#claude-ship} [长文]：Claude Ship 由三部分组成——已正式可用的 Code Review（多角度深审 PR，对发现做对抗式复核、分类后评论，每个仓库可选 Quick / Standard / Deep 三档）、测试版 PR Steward（处理失败的 CI、合并冲突和评审意见，每次推送后说明改了什么、怎么撤销，可用 @claude 指挥或 @claude stop 叫停，设计上不批准也不合并）、测试版 Claude Approvals（按团队写进仓库的策略文件自动批准常规改动，或在特定情形要求人工签字，类似「更聪明的 CODEOWNERS」，可参考 Code Review 结果和自定义的自然语言分类器）。用法两种：开发者更新 Claude Code 后输入 /ship，Claude 推送、开 PR、审查并处理反馈；Team / Enterprise 管理员可按仓库开启，自动作用于全队 PR，设定审查深度、触发时机和每月花费上限，继续沿用分支保护规则。按 token 计费，仅支持 GitHub 上 Team 与 Enterprise 计划的仓库；符合条件的 Enterprise 组织可领至少 1 万美元额度（30 天内用完，2027 年 1 月 15 日前领取）。官方称 Claude Code 团队 6 月到 9 月合并的 PR 增加一倍多，被回滚的比例下降超过 40%（Code Review 只是其流程的一层）。Boris Cherny 说一年前 Opus 4.5 已写他 100% 的代码，但发 PR 的速度没跟上；他建议先挑一个仓库、让 Approvals 以观察模式运行直到信任它。来源：[Claude 官方文章](https://claude.com/resources/articles/introducing-claude-ship) · [ClaudeDevs](https://x.com/ClaudeDevs/status/2124959436640858475) · [ClaudeDevs 用法](https://x.com/ClaudeDevs/status/2124959440772137337) · [Addy Osmani](https://x.com/addyosmani/status/2124960211287101656) · [Boris Cherny](https://x.com/bcherny/status/2124961485801836573) · [Boris Cherny 建议](https://x.com/bcherny/status/2124961488691740941)
- **零数据保留 + 企业前沿安全防护（EFS）公测** {#claude-zdr-efs}：符合条件的 Claude Platform 组织可在零数据保留（ZDR）前提下启用 Enterprise Frontier Safeguards：Messages API 流量的加密副本存进客户自己的云存储，自动检查跨多次请求的滥用迹象并把严重风险标给客户团队复核；按工作区在 Claude Console 开启，覆盖该工作区所有模型的请求，官方称与 100 多家客户共同开发。来源：[ClaudeDevs](https://x.com/ClaudeDevs/status/2124930253344948518) · [ClaudeDevs 文档](https://x.com/ClaudeDevs/status/2124930255777591454)
- **Claude Code 桌面版侧边栏改版、Claude Academy 评测课** {#claude-code-misc-1124} [长推]：桌面版的文件、改动、终端等工具改为在会话旁以标签页打开，可并排或弹出成独立窗口，先在 Mac 推出（Theo 调侃对方在照搬 T3 Code 的功能）。邵猛介绍了 Claude Academy 免费课程「Introduction to evals」：约 1 小时、4 节课加测验（80% 过关得徽章）；以虚构咨询公司 Meridian 为例，错一次要手查约 5 分钟、每月 50 份报告能容忍 5 次错，所以门槛定为 90%；旧提示词下 Haiku 4.5 只对 42/50（84%），8 次失败中 5 次是「报告里没有风险却编出风险」，补上「何时返回空值」和「先引用原句」后 Haiku 4.5 也到 100%、仍最便宜；评测集建议从 20 到 50 条起步，10 条冒烟评测设为 PR 必过检查（通过线 88%），夜间抽 1% 到 5% 线上流量用大模型裁判打分、低于基线两个标准差才报警。来源：[ClaudeDevs](https://x.com/ClaudeDevs/status/2124978802006851961) · [Theo](https://x.com/theo/status/2124987957803446311) · [邵猛](https://x.com/shao__meng/status/2124797332051128581)

## OpenAI 与 Google
- **OpenAI 与思科开源 Shirudo：给运行中的 Linux 系统上临时「盾牌」** {#openai-shirudo} [长文]：补丁的测试和部署常要几天到几周，而漏洞利用和正常请求可能依赖同一个 Linux 操作，整体封掉会让服务下线。Shirudo（日语「盾」）用 eBPF 在系统内部特定位置运行小程序，agent 可以调查漏洞、写出有针对性的「shield」，并对照利用代码和真实负载验证；运维批准后即可在服务不停机的情况下部署。四项设计：不重启的实时防护（可先观察影响再强制执行）、机器速度的防御（人控制部署什么）、可信部署（shield 加密签名，经 Linux eBPF 校验器检查）、基于 TPM 的硬件证明记录加载和移除。受控测试中，Codex 生成的 shield 给 Java 的 Base64 解码器加了输入检查，挂到运行中的 Elasticsearch 进程上，拦下了 Java4Shell 利用尝试且服务没重启。BSD 2-Clause 许可，BPF 程序 BSD/GPL 双许可；12 月 15 日有技术网络研讨会。Greg Brockman 说「今天发现一个 bug，不代表明天能给每台机器打上补丁」。来源：[OpenAI 博客](https://openai.com/index/introducing-shirudo/) · [OpenAI](https://x.com/OpenAI/status/2124980590717911527)
- **OpenAI 困惑度倡议后续：微软报出 MAI-2 Base 0.819** {#openai-perplexity-limits}：后续：微软方面发帖支持 OpenAI 的透明倡议，经 OpenAI 许可在其评测集上报告 MAI-2 Base 的 log-perplexity 为 0.819，与 GPT-5.6 Sol 基座在同一区间，且两家用同一分词器、数字可直接比较；帖子也承认，跨实验室比较以后可能要改报 bits-per-byte，还需要别的评测集，能用 OpenAI 的数据集是特例。swyx 称「微软回应了」，并喊 Alexandr Wang 加入。李博杰说这验证了他 8 年前「压缩即智能」的猜想，并承认自己 2024 年以为 log-perplexity 降到 0.9 以下就很难再降，是判断错了。反对声音：LeCun 转发了 Ziv Ravid 的线程，后者称被这篇文章「气到」，周末带着 agent 做了实验反驳。来源：[微软方面帖子（swyx 转引）](https://x.com/swyx/status/2124780264916423021) · [李博杰](https://x.com/bojie_li/status/2124701653966434701) · [Ziv Ravid（LeCun 转发）](https://x.com/ylecun/status/2124840568249307573)
- **OpenWorks：OpenAI 出钱请本地 AI 专家帮小企业** {#openai-openworks}：OpenAI 新项目 OpenWorks 资助本地 AI 专家，免费帮小企业搭工具、学技能，正在招募愿意教人的 AI 专家和想用 AI 的小企业主。来源：[OpenAI](https://x.com/OpenAI/status/2124922133545714160)

- **Hugging Face：怎么建并维护一个 agent 评测** {#hf-agentic-evals} [长文]：文章指出 agent 评测高度依赖软件环境：固定模型只换 harness，Terminal-Bench 上准确率最多相差 29.9 个百分点；98.2% 的「模型×基准」分数只有一方报告。作者用 Harbor 框架改造 Terminal-Bench 的拉曼光谱拟合任务做演示，第一版就有漏洞——一个跳过拟合、直接读数据的「捷径」脚本 8 题全满分；修好后 GPT-OSS-120B 在 24 次运行中过 11 次，失败多是过早宣布完成（19/24）。基准本身也常出错：Terminal-Bench 2.1 修了 89 个任务中的 28 个，OpenAI 审查 SWE-bench Verified 时在所查的 138 题中发现 59.4% 有实质问题。建议「分部分开源」：公开环境、harness、评分方法和公开任务轨迹，保护在用的测试集但提供受控审查渠道。来源：[Hugging Face 博客](https://huggingface.co/blog/agentic-evals)
- **vLLM：agent 的 KV 缓存直接放 NVMe，跳过 DRAM 层** {#vllm-nvme-kv} [长文]：agent 多轮会话里中位每轮 14.2 万输入 token、96% 以上是已见过的前缀，命中率每提高 1 个百分点吞吐约多 10%。在 AMD MI355X 上用 vLLM + MoRI UMBP 测试，1.8 TB 的 NVMe 池与同大小 DRAM 池吞吐差距在 1% 内（70 并发时 13492 对 13380 token/秒/GPU），只需约 80GB DRAM 做缓冲；1.8 TB DRAM 池标价约 7.6 万美元，只能保存 Kimi-K3 最近二三十分钟的 KV，而能存一天 KV 的 NVMe 池约 5.9 万美元。关键调整是把段文件从 4GiB 改成 256MiB。代价：96 并发时每小时写入 3.5 TB，SSD 磨损要考虑；轻负载下命中仍会让首 token 多约 0.4 秒；结论基于每 token KV 较小的混合架构模型。来源：[vLLM 博客](https://vllm.ai/blog/2026-11-23-skip-the-dram-tier)
