## Agent 与开发工具
- **Claude Code 团队怎么做验证：端到端、属性、差分三种测试，加一套「防作弊」规则** {#claude-code-verification} [长文]：Addy Osmani 在 Anthropic 开发者博客写道，Claude Code 团队约 90% 的代码由 Claude 编写和审查。内部测试里，让单独的评分器按评分表检查 Claude 的结构化文件生成，任务成功率最多提高 10 个百分点，越难的题提升越大。推荐三种测试：端到端测试最难被糊弄；属性测试（如编码再解码得回原值、余额永不为负、操作做两遍等于一遍）用测试库生成成千上万输入；差分测试拿旧系统当标准答案，适合大规模迁移。团队做法：在仓库里放名为 verify 的 skill，让 Claude 提交前把应用真正跑一遍；检查连续三轮还失败就停下叫人；维护一份 39 项的可靠性清单，每项都有能从 diff 里读出的触发条件，Claude 只查命中的那几项（通常 3 到 10 项）；不靠叠加更贵的第二个审查者，而是调好一个审查者并写 REVIEW.md；审查规则从基础分支读取，改动不能修改评判它的检查；每个 commit 标注验证方式（包括「none」），新闸门先用 observe 模式只记录不拦截。不稳定的测试不许加 sleep 或反复重试，找不到根因就删掉并写明原因。来源：[Anthropic 开发者博客](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- **Philipp Schmid：harness 删掉 90%，分数差不到 6 分，费用差一倍多** {#harness-delete-90} [长文]：Google DeepMind 的 Philipp Schmid 在 AI Engineer Code Summit 2026 分享，他大约每半年把编码 agent 的运行框架推倒重来一次，最近只留一个 Bash 工具，计划和记忆都放进文件系统；系统提示加工具定义从 2025 年中期 16 个工具约 12400 token 降到 574。用 Gemini 4 Carbon 跑 DeepSWE 1.1 的一道题，8 个结构化工具走了 47 次模型调用、4.2M token，只用 Bash 是 18 次、1.7M token。在他自有的 350 多项任务上用 Gemini 4 Argon 比较四种框架，分数落在 6 分以内、token 相差 39%；只用 Bash 分数最高（74.9%）却最贵（每项 5.33 美元），最省的是 Bash 加看图工具（每项 2.33 美元、89% 缓存命中）。他强调每项任务只跑了一次，小的分差可能是噪声；而且弱一些的模型（Gemini 3.5 Flash）删了工具也不会自己学会合并步骤。下一步可能是让模型直接写 TypeScript 或 Python 执行。转述与解读：[shao__meng](https://x.com/shao__meng/status/2122211754763489767) · [演讲文字稿](https://ai.engineer/code/2026/talks/philipp-schmid)
- **Claude Code 桌面版：iPhone Duo 模拟器公测、Xcode 插件进官方市场** {#claude-code-ios-duo}：Claude Code 桌面版现在支持在 iOS 模拟器里跑 iPhone Duo（公测），可以把应用放在对话旁边运行，Claude 能折叠、展开设备测试每种布局；改造已有应用时可安装苹果的 App Resizability skill 扫描布局问题，Claude 改完你同意的部分后在 Duo 模拟器里检查（需 macOS、Xcode 27.1 或更新）。在终端里工作的人，现在也能从官方插件市场装 Xcode 插件，让 Claude 构建、运行、测试应用，渲染 SwiftUI 预览和搜开发文档。来源：[ClaudeDevs](https://x.com/ClaudeDevs/status/2122439098740674839) · [Xcode 插件](https://x.com/ClaudeDevs/status/2122439104419790958)
- **「No AI Slop 宣言」：你花的心思，少于要别人花的理解成本，就是 slop** {#no-ai-slop-manifesto} [长推]：AI Engineer Code Summit 讲者和参会者合写的宣言参照 2001 年敏捷宣言，提出五组对照：结果重于产量、理解重于速度、自己的思考重于模型第一稿、更好的工作重于更省事的工作、改进系统重于修补输出。宣言不反对用 AI 或凭感觉写代码，反对的是把模型产出转手发出、不对质量负责。Horthy 发帖时称已有 300 多个签名并上了 Hacker News 首页；据 shao__meng 统计，Gist 上已列出 504 个签名。来源：[shao__meng](https://x.com/shao__meng/status/2122156731300212773)
- **后续：从「给任务」到「给目标」** {#goal-engineering}：Harrison Chase 发文说，模型变强后 agent 正从做任务（写这封邮件、修这个 bug）转向追目标（维护一个博客、让产品成功），即从指定动作变成指定结果、从一次性任务变成持续责任；agent 要自己拆任务、会调用你事先想不到的工具，所以需要能看见它在做哪些任务的待办清单。LangChain 同时转发他与 Actively AI 合写的 Goal Engineering 一文。来源：[Harrison Chase](https://x.com/hwchase17/status/2122391663889039828) · [LangChain](https://x.com/LangChain/status/2122334744390357410)
- **主会话用便宜模型、子线程用强模型？宝玉的分法** {#agent-routing-1117} [长推]：宝玉认为「主会话 + Thread」模式优化好了 token 消耗还好：主会话像公司前台，只负责甄别和路由，Sonnet 5.5 级别就够；真正干活的 Thread 用更强的模型（他在 Claude Project 里主会话用 Sonnet 5.5、子任务用 Opus 5.5）。主会话消息稀疏、缓存难命中，缓存过期后只发最近几条加会话检索；Thread 则建议在缓存快过期（如一小时缓存的第 50 分钟）时压缩上下文。有网友做数学研究，认为统筹的主 agent 应该更强；宝玉回应两者场景不同，具体研究任务就该让强模型（如 Fable）计划、调度和验收。来源：[宝玉](https://x.com/dotey/status/2122162706606121396) · [回应](https://x.com/dotey/status/2122412845656609046)
- **个人 agent 的通知疲劳；Muse 的 Chrome 扩展装了 10 万次** {#personal-agent-fatigue} [长推]：Alex Volkov 说，一封来信会引出十条关于同一封邮件的主动提醒，把它的重要性放大十倍；多位重度测试者都有同样的疲劳。接入个人 agent 要花力气，所以很黏，但没有简单的退出办法，只能暂停通知或让它少主动，这又失去了意义。他转引的观点是：接上全部联系人和连接器后，现实中只能用一个，因为太吵。另一条里他说，Muse 一周前推出、能让 Muse 用你自己浏览器的 Chrome 扩展已装了 10 万次、评分 4.5；有用户说 Muse 主动建议装它，以免云端浏览器被亚马逊等零售商拦截。Ethan Mollick 则认为 OpenAI 的 Dot 能力不差，但单线程对话、缺少地图之类的内嵌生成元素、看不到它被分派了哪些任务，界面上越来越落后于 Muse 和 Duet。Dani Avila 说，瓶颈已经不是能跑多少个 agent，而是自己记不住启动了什么、为什么。来源：[Alex Volkov](https://x.com/altryne/status/2122389714296836257) · [Muse 扩展](https://x.com/altryne/status/2122392815070290369) · [Ethan Mollick](https://x.com/emollick/status/2122405206184829341) · [Dani Avila](https://x.com/dani_avila7/status/2122107675786047948)
