## Agent 工程与开发实践
- **Netflix 用本体把可观测性做成知识图谱，省掉排障里「拼关系」的四小时** {#netflix-observability-ontology} [长推]：meng shao 的中文长文解读。问题场景：Jake Paul 对 Tyson 那场直播约 6500 万并发流，日常每天 20 亿以上请求、每秒约 3800 万条实时日志事件（文中数字）。一次首页渲染慢约 1.5 秒的回归，嫌疑可能在客户端版本、A/B 实验、基础设施限流或下游六跳之外的 GraphQL 坏数据，调查花约 4 小时，大部分时间不是在解难题，而是在重建各系统本来知道、却从没写成可发现关系的映射。Netflix 的判断是这本质上是数据建模问题，于是建了 Observability Ontology 和 RDF 知识图谱：用 RDF、OWL、SHACL、SPARQL，存在自研的 RDF 四元组库 QuipuDB（基于 Rust 的 redb），每次采集导出 Turtle 归档便于对比，约 12 个命名空间覆盖运维领域。关键设计包括拒绝泛化的「Service」，统一成 ops:Application 并对照约 4.9 万条软件目录校验；把 Slack 事故讨论里的假设、被否定的路径和缓解手段结构化成三元组。LLM 摘要、模糊匹配这类不确定输出，通过本体的类型约束收成确定性三元组。关联引擎读 13 类信号，在约 10 分钟窗口内找路径，置信度低于 0.6 的链丢弃，结果是带证据的假说而不是结论。落地形态是 AutoRCA：多个专科 agent 用同一套本体词汇协作，告警照响、人照样拍板，省下的是找负责人、拼发布记录、跨系统关联。文章给了自建的八条原则，比如先建模身份和权威目录、本体当代码走 PR 评审、用类型系统约束随机工具、人审批 agent 和本体的变更。下一步是高置信自动修复和预测性自愈，并计划和 Netflix UDA 的领域建模语言 Upper 对接。来源：[meng shao](https://x.com/shao__meng/status/2113925598443675835)
- **Shopify 给 agent 配远程移动开发机，agent 产出的已合并移动端 PR 占比从 6% 升到 61%** {#shopify-remote-dev} [长推]：Shopify 的 mustafa01ali 发帖，meng shao 写了中文拆解。Shopify 在 Slack 里的 agent 叫 River。移动端一开三四条 agent 工作流，本机就被编译器和模拟器吃满，于是搭了 Remote Dev：远程 Mac 机群装好 iOS 模拟器，因为云 Mac 不支持嵌套虚拟化，Android 模拟器放在开了嵌套虚拟化的 Linux VM 上，再挂到同一个 SSH 会话。冷启动（检出巨型 monorepo 加首次编译）曾超过 30 分钟，改成预热池以后，「在设备上看到改动」缩短到几分钟。每个 River 会话独占一套环境，可以并行改代码、编译、跑测试、在真模拟器里点 UI 并录前后对比，还能通过 WebSocket 把远程模拟器画面推到浏览器做实时预览，设计师和 PM 也能通过 Slack 改移动端。他们用 skill 加封装 SSH 的 CLI 教 agent 用远程机器，长任务用 tmux 让 River 实时观察。采纳上也有心理障碍，团队专门做了仿「Mac vs PC」的内部广告。还用便宜的分类模型 Jev 给移动端对话打标签，把失败案例拿去找改进点。来源：[mustafa01ali](https://x.com/mustafa01ali/status/2113269013694271940) · [meng shao](https://x.com/shao__meng/status/2113799609671909827)
- **复杂的 agent 记忆并不总是必要：朴素 RAW-RAG 在长对话记忆评测上更强** {#raw-rag-memory} [长推]：elvis 推荐、meng shao 详细解读的论文。RAW-RAG 不做任何 LLM 抽取、摘要或构图，只把对话按 256 token 窗口（重叠 32）建扁平向量索引，查询时余弦检索 top-128，再用 cross-encoder 重排取 top-15 交给读者模型。在 LoCoMo、LongMemEval、MEME、MemoryAgentBench 上，7 组「基准乘模型」里有 6 组第一，比最强的 agentic memory 系统高 0.13 到 5.53 分；唯一落后的是 MEME 加 DeepSeek-V4-Flash（MemMachine 44.71 对 43.19）。两个预实验动摇了「必须显式维护状态」的假设：审计 Mem0 发现，LoCoMo 上 UPDATE 和 DELETE 只占写操作的 4.39%，关掉它们准确率反而从 67.36% 升到 69.42%。消融显示去掉重排降 3.92 分，只返回 1 条降 11.73 分，加原子事实抽取、摘要增强或图扩展都没超过默认版。在 BEAM-1M 上摄入只要 0.3 小时，Mem0、MemOS、Memora 等要 3.2 到 27 小时。作者的解释是瓶颈在证据覆盖率，把历史改写成记忆条目会丢掉回答所需的关系和依赖路径，即使给完整的改写后记忆库，也不如原始证据。局限是只测了离线公开对话基准，原文存储还有隐私和删除的现实代价。来源：[meng shao](https://x.com/shao__meng/status/2113803928869744647) · [elvis](https://x.com/omarsar0/status/2113635562578178147)
- **Agentic SDLC 不等于软件工厂：Qodo 创始人谈「有边界的 L4」** {#agentic-sdlc-l4} [长推]：Qodo 创始人 itamar_mar 的长文，meng shao 中文整理。他认为各开发阶段都有 agent 参与，并不等于有了软件工厂。他仿照自动驾驶分级：L2 是 agent 干大块活、人主动监督；L3 是限定条件下能跑完交付流，但人仍是必需的批准或救援；L4 是对有边界的一类变更，能走完授权的生命周期（验证、允许的发布动作、安全回退），失败时不依赖人及时介入；L5 是几乎覆盖全部软件工程。他强调运行边界本身就是能力的一部分，可以对「成熟内部服务的例行变更」冲 L4，对支付授权这类仍然紧控。走向 L4 要多做五件事：界定工作本身、让成功可评估、验证要经得起「生成方的激励」（第二个叫 reviewer 的 agent 不等于独立）、用证据而不是自信放行、安全回退。度量要看合格工作完成率、剩余人工、逃逸和失败成本，而不是 agent 数量或生成行数。口号是 System > Agents > LLMs，团队要自建并拥有这套系统。来源：[itamar_mar](https://x.com/itamar_mar/status/2113255396299128887) · [meng shao](https://x.com/shao__meng/status/2113923043936612792)
- **Claude 工程负责人 Felix Rieseberg：别再用 2024 年的方式用 Claude** {#felix-rieseberg-interview} [长推]：meng shao 整理 Felix 接受 siliconvalleymm 访谈的要点。他现在几乎不写代码，说团队约一周半做出了 Claude Cowork。核心观点：不要当「传送带」挑一条崩溃丢给模型，而是让模型直接看全部崩溃数据，自己决定修什么。他认为行业对「agent 角色扮演」用力过猛，多数任务他不设人设；与其给每个 agent 切一小片数据，不如给全景业务视图和文档清楚的工具。Skills 他劝慎用，说半衰期极短，有时删掉 skill 输出反而更好。防幻觉的实用招是对抗评审：同一产出开多条线程专门「证明你错了」，再开一条当裁判筛选哪些批评成立；他最不信的是同一个会话给自己打分。他更在意「增强」而不是「自动化」，认为今天的 AI 产品大概还在智能手机之前的功能机阶段。对工程师的建议是证明共情和整合多个系统的能力，背单一 API 会贬值。来源：[meng shao](https://x.com/shao__meng/status/2113970197161988276)
