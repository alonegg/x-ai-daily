## Agent 工程与开发实践
- **Claude 博客：什么时候该把子 agent 折回主循环，Skills 渐进披露常胜过多专家编排** {#claude-single-loop-skills} [长推]：meng shao 对 Claude 博客文章的中文拆解。问题场景：大企业里多条产品线要进同一个客户入口时，各团队先自建 agent，平台再盖一层编排（orchestrator 加 subagent，或者把子 agent 当 MCP 工具），结果马上碰到跨 agent 丢细节、子 agent 重叠且没人负责、「Frankenprompt」（人人往系统提示里加一句，规则冲突、语气不一）、各自优化局部 eval 而没人维护端到端质量，以及延迟：一家客户对比多 agent harness 和单循环，后者约快 2 倍。文章说，「每个问题类型、每个团队一个子 agent」往往是康威定律，不是能力上限。子 agent 仍然适合三种情况：单循环因上下文膨胀出现可测的性能下降、多个任务需要并行并用完即丢的新上下文、单 agent 选不好工具或系统提示里指令打架；Anthropic 自己的多 agent 研究系统也在用。更好的默认是一个模型、一个上下文窗口、开放式工具循环，用 Skills 渐进披露上下文、用 tool search 渐进披露工具；理由包括长程任务里前几步结果留在同一窗口更好串联，以及模型变强：Claude Code 针对更强的模型把系统提示砍掉了 80% 以上，自 Opus 4.5 起单循环能扛的远超多数团队预期。迁移路径分四步：先建任务完成度 eval（哪怕先有 10 条黄金样例）；合并领域 agent；把子 agent 当工具；再一次折一个，变成 Skills 加 MCP 工具，对比前后每个任务的翻盘情况。文中举的例子是，折入后延迟降了，但主 agent 自己用订单查询工具答完，没再去问物流专员要送达日期，原本能过的流程断了，而且这个断裂两次运行里只出现一次。多团队共养一个 agent 时，所有权从「各养一个 agent」变成「养 Skills 和工具」，系统提示里工具定义超过约 30 到 50 个后选型容易变差，应按用户意图组工具，而不是一个 API 一个工具。配套的迁移工具有 /claude-api 下的 build-eval、prompt-audit、hillclimb、cost-optimize。来源：[meng shao](https://x.com/shao__meng/status/2114164780986679331)
- **CMU 与 Google 研究规格驱动开发：266 个仓库、21 位开发者访谈** {#sdd-cmu-google-study}：Daniel Avila 说 X 上关于 SDD（Spec Driven Development，先写规格再让 agent 实现）的争论很多，不如看研究和数据。他读的这篇 CMU 和 Google 研究者的论文分析了 266 个仓库，访谈了 21 位实践者。发现包括：77.6% 的规格里写了实现细节；开发者反映 agent 更可靠了，但计划和评审的开销也更大；研究者没法把 SDD 的好处和 AI 模型本身的进步区分开。他的看法是，SDD 有用可能只是因为它逼人想清楚自己要什么，并追问：编程 agent 和大模型越来越强，SDD 还需要多少？来源：[Daniel Avila](https://x.com/dani_avila7/status/2114486060730237224)

## 模型与基准
