## agent 工程：MCP、谨慎与分层
- **MCP 之争：agent 几乎不用，但它可能是「没有契约的 API」** {#mcp-without-contract} [长推]：Steve Lacey 说他在自己的应用里都做了 MCP，可自己的 agent（每个是一个带独立项目目录和 .env 的 Claude Code 会话）几乎从不选它：不是 MCP 不好，而是多数环境里要人先安装配置连接器，agent 做不了这一步，只能停下来叫人，而它直接调 API 或开浏览器就行；他发现有的 agent 悄悄绕开了专门为它们做的 MCP 服务。这也让「复制这段提示词开始用」按钮失效，粘进普通 ChatGPT 对话后第一件事就是让人去装连接器。他仍做 MCP 的理由：API 契约是为了不让调用方代码崩，要版本化、慢慢弃用、长期兼容；agent 没有要维护的调用代码，每次现读文档，所以可以随时重写，还能暴露传统 API 懒得做的能力，比如建账号、换头像、删账号。他的结论是连接器、目录和安装流程会消失，留下的 MCP 意味着「没有契约的 API」。levelsio 说他以前也因此反对 MCP，现在给自己的网站加 MCP 只是因为大家期待有，长期看 MCP 和 API 会合并成一个，都支持 API key 和账号级 OAuth。来源：[levelsio](https://x.com/levelsio/status/2117361943938031845) · [Steve Lacey](https://x.com/stevelacey/status/2117359574181163199)
- **Thoughtworks：资深开发者为何仍对 coding agent 谨慎** {#senior-devs-agent-caution} [长推]：meng shao 整理 Rachel Laycock 的文章。她认为资深开发者的谨慎不只是爱写代码或怕失业：他们问的是行为、边界对不对，能否演进，失败了怎么办，别的团队能否接手；而且用这种方式建系统几乎还没有长期生产经验。欧洲区 CTO Giles Alexander 带团队做了一周「人不写代码、全交给 agent」的实验，做出了约八成的航空类应用；人大部分时间在白板上理领域、画边界、给 agent 可执行计划，并设计测试、契约、架构检查和交付流水线等反馈回路，粗估三分之二时间在白板、三分之一在 harness，提交功能代码最多的反而是产品同事。但构建经常是红的，「在我机器上能跑」回来了，常红的构建会让告警麻木；原因可能是并行 agent 互相踩改动、系统不够模块化或变更比检查快。她认为持续交付和 DevOps 会迎来重审，并引 DORA 2025：AI 采用与更高吞吐相关，却与更低交付稳定性相关。内部还在争论人不逐行读代码、测试也由 agent 生成时 TDD 的角色，以及批次该多大。Martin Fowler 指出她的「成年人学滑雪」比喻不够：agent 开发更像未知野地，几乎没人安全走完全程。她建议领导别用「agent 产出多少代码」当成功标准。来源：[meng shao](https://x.com/shao__meng/status/2117092563329179702)
- **Arca 的 AI 负责人：按任务分模型，钱不交给 agent 动** {#arca-task-routing}：Latent Space 转发 theahmedkaiz 整理的 Arca 的 Aman Singh 访谈。一是模型分层：做税务规划或税务分析这类任务用最重的模型，大量后台活动用低一档的模型；整理者的观点是每个任务需要的智力有上限，比如发票对采购单只有一个正确答案，企业把一切都路由到最强模型会多付钱，他称多数企业任务只需便宜模型或普通代码，平均只有约 1% 的调用真正需要前沿模型。二是护栏：分析完全自动化，但移动资金、清算资产甚至直接联系客户都必须有人在环，agent 会拉来合适的人并给出可审可改的计划；工作流应分到代码、agent、人三种各有盲区的方案里互相弥补。来源：[theahmedkaiz（路由）](https://x.com/theahmedkaiz/status/2117220843944112477) · [theahmedkaiz（护栏）](https://x.com/theahmedkaiz/status/2116963663844171845)

- **企业 AI 的五层：RAG、知识图谱、语义层与 agent 别混为一谈** {#ai-layers-five-verbs}：Connected Data 转发 Thilo Hermann 的系列文章：数据目录负责「找」（在哪、能不能用），RAG 负责「取」（不会计数、不会关联、不知道是否最新），语义层负责「定义」（比如公司说的「收入」是什么），知识图谱负责「连接」（跨系统识别同一实体），agent 负责「行动」（需要记忆、跟随用户的权限、工具契约、时间概念和可追溯）。他举的架构咨询助手早期会给出流畅、引用充分、但基于已被替代的旧规范的答案，改进来自分块元数据（来源、负责人、最近审阅、有效期），而不是换更好的模型。来源：[Thilo Hermann（Connected Data 转发）](https://x.com/TheYotg/status/2116129027517714921)
